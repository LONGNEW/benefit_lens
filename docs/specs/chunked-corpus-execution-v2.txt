BenefitLens 청크 병렬 실행 v2
적용일: 2026-11-20 07:48 KST

목적
268,925개 문맥 묶음의 순차 대기를 줄인다. 기존 50개 단일 호출을 최대 100개 청크 4개의 동시 호출로 변경한다. 동시에 진행할 수 있는 입력은 최대 400개다. 실측 속도는 호출 지연과 출력량에 따라 달라진다.

실행
python3 tools/run_benefitlens_codex_corpus.py --batch-size 100 --concurrency 4 --max-input-characters 160000 --timeout 900 --reasoning-effort low
서비스: benefitlens-codex-corpus-20261120.service
후속 자료 갱신: benefitlens-team-handoff-20261120.service
max-batches를 생략해 기존 대기 큐 전체를 처리한다. 모델과 전역 사용자 설정은 유지한다.

청크와 쓰기 계약
1. 공고와 경험에서 번갈아 pending을 선택하고 영수증 경로와 함께 선점한다.
2. 요청 본문과 시스템 지시가 160,000자를 넘으면 청크를 나눈다. 청크를 줄이기 위해 원문을 자르지 않는다. 경험 문맥의 기존 최대 900자 추출 규칙은 유지한다.
3. 서로 다른 청크 4개의 Codex CLI 호출을 스레드 풀에서 실행한다. 스레드는 프로세스 실행과 각 청크의 파일만 다룬다.
4. 큐 변경, 스키마와 원문 인용 검증, 영수증 재생과 결과 저장은 부모 스레드 하나가 순서대로 수행한다.
5. 정상 그룹은 저장하고 불확실하거나 검증에 실패한 그룹은 이유와 함께 보류한다. 성공한 형제 그룹을 다시 호출하지 않는다.

변경한 범위
CLI는 batch-size 40~200, concurrency 1~8을 허용한다. 이번 실제 운영값은 100과 4다. 공고 응답 배열 상한을 200으로 늘리고 조건 매핑의 필드와 원문 검증 규칙은 유지했다. 각 요청의 입력과 스키마 해시를 보존한다.

한도와 재개
공급자 한도나 인증 오류가 관측되면 새 청크를 선점하지 않고 이미 실행 중인 응답을 수거한다. --resume-provider는 명시적으로 재개할 때만 사용하며, 병렬 호출에서 발생한 모든 소유 대기 영수증을 복구한다. 실제 완료된 출력은 재호출하지 않고 재생한다.
SIGTERM, SIGINT 또는 codex-corpus-v1/drain.request는 추가 선점을 멈추고 진행 중인 청크를 수거한다. 서비스는 KillMode=mixed, TimeoutStopSec=1200으로 부모의 배출을 기다린다. drain.request를 사용한 재시작은 파일을 제거한 뒤 실행한다.

상태와 후속 연결
codex-corpus-v1/runtime.json: 실제 청크 크기, 병렬 수, 문자 예산과 추론 설정.
codex-corpus-v1/progress.json: 현재 실행 목록, 이번 프로세스의 제출과 완료 배치 수.
codex-corpus-v1/ledger.sqlite: 실제 배치별 실행 상태와 사용량.
후속 조정자는 기존과 같이 25개 실제 완료 배치마다 경험 품질, 조건 질문과 작성 자료를 갱신한다. 분석 워커 안의 동기 handoff 호출을 운영 명령에서 빼고 전용 갱신 서비스가 담당한다.

검증
동시 실행 중 입력 중복, 청크 문자 예산, 공급자 오류 이후 추가 호출 차단과 전체 대기 복구, 진행 중 결과의 배출을 합성 테스트로 확인했다. 문맥 수와 원문 수, 내용 검토 완료량은 따로 보고한다. 속도 비교는 실제 CLI 장부의 새 실행 시점 이후 완료량과 벽시계 시간으로 계산한다.
