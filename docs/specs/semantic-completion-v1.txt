실제 의미 분석 완료와 작성 패턴 인계 계약 v1

목적
후보 수, 원문 수와 정형 전처리 수를 LLM 분석 완료 수와 구분한다. 인계 도구는 기존 큐와 저장 결과를 읽으며 모델 호출, 네트워크 요청이나 정본 DB 쓰기를 실행하지 않는다.

입력과 실행
도구: tools/build_benefitlens_semantic_handoff.py
기본 큐: /home/longnew/.cache/datasets/benefitlens/scale50k-20261109/team-production-20261119/semantic/queue.sqlite
실행: python3 tools/build_benefitlens_semantic_handoff.py
출력: 같은 루트의 handoff 디렉터리

완료 단계
1. model_output_preserved_tasks: 실제 출력 JSON, Claude CLI 호출 영수증, invocation_id, 입력 지문과 입력 파일 해시, 출력 해시, 원응답 해시가 대조된 작업 수.
2. source_validated_tasks: 1단계를 통과하고 작업 상태가 completed이며 별도 validation 파일에 valid=true와 원문 검증 범위가 있는 작업 수.
3. llm_completed_source_validated_units: 단위의 상태가 completed이고 지정된 모든 청크가 2단계를 통과한 원문 단위 수. 단위 aggregate의 입력 지문, 작업 참조 집합, 결과 해시와 경로도 대조한다.
4. independent_human_approved_units: 현재 결과 해시와 연결된 가림 심사에서 독립 사람 검토자 2명이 원문과 명시 기준을 검토하고 승인한 단위 수.

부분 청크만 끝난 원문은 1, 2단계의 작업 수에만 포함한다. 여러 작업이 같은 Claude 배치 호출을 공유하면 invocation_id를 중복 제거한다. distinct_output_preserving_model_invocations는 보존 출력 영수증이 확인된 호출 수이며 실패와 무출력 호출의 총시도 횟수는 운영 워커가 별도로 집계한다.

인용 구간, 자료형과 인물 귀속에 대한 기계검증은 워커의 T1/T2 validator 결과를 소비한다. 인계 도구는 파일과 영수증의 연결을 다시 대조한다. 해시가 맞아도 모델의 해석이 정확하다는 판단은 T3의 내용 검토 대상으로 남는다.

공통 스키마 인계
notice-common-schema-candidates.jsonl은 검증된 공고 결과와 출처 결과 경로를 연결한다. 각 행은 source_validated_common_schema_candidate이며 production_database_written=false다. 공통 필드와 프로그램별 정보를 정본에 반영하는 승인 및 저장 경로와 분리한다.

작성 패턴 인계
writing-pattern-observations.jsonl은 검증 완료된 경험 단위마다 single_case_observation 한 개를 만든다. 문항의 명시 요구, 공식 안내, 관찰된 전략과 추정 의도를 T2가 부여한 layer 그대로 보존한다. 다음 자료와 실행 결과를 연결한다.
- events: 동기, 상황, 개인 역할, 선택, 행동, 결과, 성찰과 향후 활용.
- writing_observations: 의도 축, 재료 선택과 전이 가능한 전개 후보 및 적용 한계.
- paragraph_observations: 문단 역할과 목적, 첫 문장과 마지막 문장의 기능, 주장, 근거 사용, 추론, 이전 및 다음 문단과의 연결.
- evidence: 원문 문서와 구간, 인용과 본문 해시.

지원자와 경험 식별자는 출처 내부 귀속용이다. 타인의 경험을 사용자 사실로 채우지 않는다. 인물과 회차의 독립성을 검토하지 않은 여러 행을 반복 성공 사례로 세지 않는다. 현재 인계는 사례 간 공통 성공 패턴을 승인하지 않으며 품질 점수를 비워 둔다.

프로그램과 실제 공고 회차의 연결
출처의 프로그램명이나 ID만 있으면 inferred_candidate, 식별자도 없으면 unknown이다. verified 연결에는 별도 검토 파일의 경로와 해시, valid=true, 일치하는 프로그램과 회차 및 공고 링크, 근거 참조가 필요하다. 원래 program_binding도 보존한다.

내용 검토 기준
pipeline/config/writing_evidence_framework_v2.json의 요구 → 주장 → 근거 → 추론 → 문단 → 문서 연결을 참조한다. 일반 기준, 장르 요구와 사용자의 문단 연결 선호를 구분한다. 한 사례의 관찰, 지원서 작성 제안과 효과가 입증된 패턴은 별도 상태다.

독립 심사 입력
옵션 --reviews 파일은 배열이며 각 기록에 unit_id, output_sha256, reviewer_id, reviewer_type=human, independent_of_generation=true, blinded=true, source_review_performed=true, criteria_refs와 verdict=approve를 요구한다. 서로 다른 사람 2명이 현재 결과에 승인해야 4단계로 집계한다. 심사 기록을 주지 않은 실행의 승인 수는 0이다.

출력과 검증
summary.json: 공고와 경험별 단계 수, 실제 완료와 파일 불일치 오류.
completed-unit-handoff.jsonl: 확인된 단위와 결과 해시, 기계검증 및 사람 심사 상태.
나머지 두 JSONL: 공통 스키마 후보와 사례별 작성 구조.
테스트: python3 -m pytest -q tools/tests/test_benefitlens_semantic_handoff.py
합성 fixture로 불완전 청크, 파일 변조, 모델 미호출, 원문 검증 누락, 호출 중복, 잘못된 프로그램 연결과 심사 누수를 검사한다. 테스트 결과는 실제 LLM 분석 건수나 글쓰기 품질 평가로 집계하지 않는다.
