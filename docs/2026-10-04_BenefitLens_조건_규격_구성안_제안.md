# BenefitLens 조건 비교 중심 구성안 제안

상태: **팀 검토용 설계 제안**. 기존 구현의 변경, 팀의 확정 결정 또는 학생의 장학 자격 판단을 뜻하지 않는다. 확인일은 2026년 10월 3일 UTC이며 한국 시간으로 10월 4일이다.

제안 발표에서는 **저장된 공고와 제도 안내 몇 건을 같은 규격으로 정리하고, 가상 학생의 학적·성적·학자금 지원구간과 비교해 근거를 보여주는 흐름**에 집중하자. 기본 조건은 7개 코드로 시작하고 특정 공고에 필요한 조건만 추가한다. 설명문은 근거와 안내에 남기고, 조회는 검토한 타입·단위·연산자와 논리 트리로 계산한다. 신청서 초안은 기말 목표에 연결할 후속 단계로 둔다.

기존 사용자 지시는 학교 범위를 POSTECH으로 제한하고, 자유문과 비교용 조건을 분리하며, 카드에는 지원 자격·조건·혜택·특약·기간을 간결하게 보여 달라는 것이었다. 참여 의사·교육·출석 등은 신청 후 해야 할 일로 분리하고, 공개 상세 페이지·FAQ·규정에 있는 내용은 연결해서 확인하라는 요청도 있었다. 따라서 이 제안은 같은 목적을 유지하면서 기본 입력과 비교 규격을 좁히는 안이다.

수업 일정은 위임 요청에서 확인한 **제안 발표 10월 20일 또는 22일, Team 4의 정확한 차례 미확인**을 사용한다. 제안 단계의 중심은 아이디어·수집 전처리·DB 관리이고 완제품은 기말 목표다. 아래 축소 범위는 팀의 새 합의가 아니다.

## 2 저장 상태와 확인 한계

이번 작업은 기존 파일·수집 데이터·코드를 수정하거나 새 공고를 수집하지 않았다. D1 SQLite는 읽기 전용으로 조회했다. PostgreSQL 원본 바이트와 전체 본문은 이번 환경에서 직접 조회하지 못했으므로 **D1에 남은 인용·조건·출처 상태를 확인한 것과 원문 전문을 검증한 것을 구분**한다.

|---|---|---|
| `pipeline/data/exports/collection_summary.json` | 생성 시각 `2026-10-01T04:03:54.841875+00:00`; 후보 70건, 현재 구조화 규칙 194개, 미해석 규칙 74개, 공개 가능 0건 | 저장 당시 집계. 현재 신청 가능한 공고 수가 아님 |

## 4 기본 조건은 7개 코드로 시작

**제안:** 현재 36개 사전을 삭제하지 않고, 아래 7개만 기본 입력 및 조회 계약으로 묶는다. 사용자는 학교·학위 과정·학적을 먼저 입력하고, 선택한 공고가 요구할 때 성적·구간·수료 정보를 보충한다. 빈도는 먼저 모집 공고 17건과 제도 안내 53건을 각각 세어 확인한 뒤 확대한다.

| 코드 | 값 규격 | 핵심 주의점 |
|---|---|---|
| `institution` | 학교 코드, 예 `POSTECH` | 게시판 학교와 실제 지원대상 학교는 다를 수 있음 |
| `degree_level` | `undergraduate`, `master`, `doctoral`, `integrated` | 재학 상태와 분리. 현재 코드 `academic_level`에 대응 |
| `enrollment_status` | `enrolled`, `leave`, `completed`, `graduated` | 기준일 필요. 졸업 예정은 별도 예정일이며 재학과 동시에 성립할 수 있음 |
| `coursework_completed` | 참 또는 거짓, 확인 상태 별도 | 학적상의 수료와 공고가 정의한 Coursework 수료를 자동으로 동일시하지 않음 |
| `grade` | `metric=gpa|percentile`, 점수, 만점, `basis=previous_semester|cumulative|specified_term|aggregate_window|unspecified`, 학기 | 이수학점과 구분. 집계 점수는 `aggregation_scope`에 기간·학기 목록·집계 방식을 추가. GPA 비교는 같은 만점 또는 공식 변환 근거가 있을 때만 |
| `earned_credits` | 학점 수, `basis`, 학기, 단위 `credit` | “10학점”만으로 직전학기라고 단정하지 않음 |
| `kosaf_band` | 정수 구간, 적용 학기, `assessment_status=assessed|pending|not_assessed|unavailable` | 기초·차상위는 별도 자격 상태. 공고 근거 없이 0구간으로 바꾸지 않음 |

`grade`는 여러 관측값을 갖는다. 예를 들어 직전학기 GPA와 누적 GPA를 동시에 요구하는 공고에는 서로 다른 두 조건이 필요하다. 프로필에서도 둘을 한 값으로 덮어쓰지 않고 `(metric, basis, term)`별로 저장한다. 백분위 77과 만점 불명의 GPA 2.0은 서로 환산하지 않는다.

국가우수 표본의 명시적 척도는 `백분위≥87 OR (만점4.5 AND GPA≥3.50) OR (만점4.3 AND GPA≥3.30)`으로 보존할 수 있다. 다만 직전 2년 집계와 졸업필수학점의 40%는 기본 단일학기 비교보다 복잡하므로 첫 데모에서는 확인 필요로 남기고 집계 기간·분모 계약을 선택 확장하자. 직전 한 학기 GPA로 대신하지 않는다.

**선택 확장:** 표본이 요구하는 `graduate_semester`, `department`, `study_load`(전일제 여부)를 먼저 연결할 수 있다. 등록 형태가 실제로 명시되면 `registration_type`을 학적·전일제와 별도로 둔다. 지역·연령·팀 규모·중복수혜·선발 이력은 필요한 공고에서만 추가한다. 기본 필드 밖의 필수조건도 그대로 보존하며 입력·근거가 없으면 확인 필요로 남긴다.

## 5 조건의 역할과 논리

| 역할 | 조회와 화면에서의 처리 |
|---|---|
| `required` 필수 자격 | 참·거짓·미상으로 기본 조건 결과 계산 |
| `exclusion` 명시적 제외 | 제외 조건이 참이면 불일치. 미상이면 확인 필요 |
| `preference` 우대·경쟁 선발 | 자격 통과를 만들지 않음. 별도 선발 안내 |
| `document` 제출 서류 | 제출 체크리스트. 미입력을 학적 자격 탈락으로 바꾸지 않음 |
| `obligation` 신청·선발 후 의무 | 참석·교육·업무·반환 등 요구사항을 표시. 실제 신청 준비 상태는 별도 계산 |

역할은 키워드만으로 정하지 않는다. 예를 들어 “이미 재직 중인 자 제외”는 객관적 제외 조건이고, “선발 후 교육 참석”은 의무다. 법적·행정적 필수 신청 요건이 있다면 준비 체크리스트에서 미충족을 알리되, 사용자 입력이 없다는 이유로 학적·성적의 비교 결과를 바꾸지는 않는다.

현대모비스 표본의 **수정 제안 트리**는 다음과 같다. 저장본에 빠진 석사 재학 규칙을 보강하는 안이며 아직 정본에 반영하지 않았다.

```text
ANY
├─ ALL
│  ├─ degree_level = master
│  ├─ graduate_semester BETWEEN 1 AND 3
│  └─ enrollment_status = enrolled
└─ ALL
   ├─ degree_level = doctoral
   └─ coursework_completed = true
      definition = 이 공고의 Coursework 수료 기준
```

박사 경로가 참이면 석사 학기 정보가 없어도 전체 OR은 참이다. 석사 4학기이고 박사 경로도 거짓이면 거짓이다. 박사 과정이지만 해당 Coursework 정의에 대한 정보가 없으면 미상이다. `unresolved` 노드도 해당 경로 안에 놓아, 관계없는 경로의 미해석 문장이 전체 결과를 무조건 막지 않게 한다. 범위를 모르면 루트에 두고 검토한다.

| 결합 | 참이 되는 경우 | 거짓이 되는 경우 | 나머지 |
|---|---|---|---|
| AND | 모두 참 | 하나라도 거짓 | 미상 |
| OR | 하나라도 참 | 모두 거짓 | 미상 |
| NOT | 입력이 거짓 | 입력이 참 | 미상 유지 |

면제 예외는 적용 대상을 연결한다. **합성 예:** “신입생은 성적 기준 면제”라면 `다른 필수조건 AND (신입생 OR 성적기준)`이지 `신입생 OR 모든 조건`이 아니다. 예외가 GPA에만 적용되면 이수학점은 계속 검사한다. 실제 면제 문구가 없으면 이 예외를 실제 공고에 넣지 않는다.

## 6 미상은 원인과 함께 저장

값에 `unknown`이라는 문자열이나 -1을 넣지 않는다. 값은 null로 두고 상태를 따로 기록한다. 참·거짓·미상이라는 **결과**와 왜 미상인지라는 **원인**을 분리한다.

| 정보 층 | 상태 예 | 의미 |
|---|---|---|
| 원천 관측 | `present`, `not_stated`, `unreadable`, `referenced`, `conflicting` | 원문에서 읽었는지, 링크로 확인해야 하는지 |
| `normalization_status` | `normalized`, `unresolved` | 타입과 논리로 옮겼는지 |
| `review_status` | `pending_review`, `approved`, `rejected` | 근거와 해석을 검토했는지. 정규화 상태와 독립 |
| 학생 정보 | `known`, `not_provided`, `pending_assessment`, `unavailable` | 값과 시점이 확인됐는지 |
| 비교 미상 원인 | `missing_profile`, `term_mismatch`, `unknown_basis`, `scale_mismatch`, `missing_source`, `ambiguous_logic` | 추가로 확인할 한 항목을 반환 |

자료에 없다는 사실은 조건이 없다는 뜻이 아니다. 빈 규칙 트리도 자동 참이 되지 않도록 `source_coverage=complete|partial|unavailable`을 함께 둔다. 원천의 필수 구역 누락·적용 범위 불명·OCR 실패는 전체 결과를 보류한다. 적용 경로와 다른 필수조건까지 확인된 미해석 노드는 해당 경로의 미상으로만 계산한다. `normalization_coverage`는 해석된 노드 수와 미해석 노드 수를 기록하며, 미해석 개수만으로 OR 결과를 결정하지 않는다. 원문과 FAQ가 충돌하면 각각 보존하고 검토 전 선택하지 않는다.

결과는 세 축으로 반환하자.

```text
조건 비교: match | mismatch | needs_check
자료 검토: approved | pending_review | incomplete
접수 상태: open | upcoming | closed | unknown | not_applicable
```

예를 들어 “기본 조건 일치 · 자료 검토 대기 · 제도 안내”가 가능하다. 공개 화면에서 자격 검토 후보로 표시하려면 자료 승인과 적용 규정·기간도 확인해야 한다. 표현은 `등록된 조건 일치` 또는 `검토 후보`로 제한하고 선발·지급·실제 신청 자격을 확정하지 않는다.

`comparison_mode=demo_candidate`에서는 타입이 있는 검토 대기 조건의 계산 결과를 자료 검토 상태와 함께 보여준다. `approved_read` 조회는 승인한 조건집만 사용한다. 검토 대기 자체를 타입 비교의 미상 원인으로 혼합하지 않고, 승인 게이트를 통과하지 못한 자료는 해당 조회에 넣지 않는다.

## 7 원문에서 조회까지의 정보 규격

| 대상 | 제안 규격 |
|---|---|
| 식별 | 수집처 ID, 원천 공고 ID, 모집 회차 ID, 불변 공고 버전 ID를 분리. 출처 게시물 ID만으로 여러 회차를 하나로 합치지 않음 |
| 원본 | 공식 URL, 가져온 시각, MIME, 바이트 SHA256, 저장 위치, 수집 성공·실패, 마지막 정상본을 기록 |
| 텍스트 | 원본과 추출 텍스트의 해시를 별도로 기록. HTML 선택자·표 행, PDF 페이지, OCR 좌표 같은 위치를 저장 |
| 조건 | 코드, 역할, 허용 연산자, 타입 있는 값, 단위, 적용 학기·기준일·정의, 트리 위치, 근거 ID, 검토 상태 |
| 버전 | 원본 변경과 추출 규격 변경을 구분. 원문이 같아도 파서·사전이 바뀌면 새 규칙집 버전을 만듦 |
| 날짜 | 날짜만 있으면 date와 정밀도를 보존. 시각·시간대가 확인된 경우만 timestamp로 변환. 날짜뿐인 마감을 임의로 23:59로 만들지 않음 |
| 단위와 코드 | 점수·학점·구간·연령을 분리. 학교·학과는 코드와 원문 명칭 함께 저장. 별칭 합치기는 검토한 사전만 사용 |
| 누락 | null와 관측 상태 사용. 생략된 조건·서류를 없다고 확정하지 않음 |
| 참조 규정 | 조건이 인용한 규정의 버전·구역을 연결. 어떤 공고 경로에 적용되는지도 보존 |
| 검토 이력 | 승인·반려 사유, 검토 시각, 담당 식별자를 원본 후보와 연결. 이전 후보를 덮어쓰지 않음 |

현재 D1에는 개별 `opportunity_version_id`, 원본 문서 버전 ID 또는 공고 fingerprint가 전달되지 않는다. `criteria_version`은 조건 사전의 버전이고 `source_updated_at`은 이를 대신할 공고 버전이 아니다. **제안:** 조회 결과에도 `notice_version_id`, `rule_set_version`, `evidence_id`를 보내 과거 결과를 재현할 수 있게 하자. 전체 D1 데이터셋 버전은 복제 묶음 식별자로 별도 보존한다.

## 8 최소 스키마와 조건 예시

새 DB를 병렬로 만들기보다 기존 PostgreSQL 테이블에서 **다음 논리 계약에 필요한 열과 관계만 사용하는 조회 뷰**를 먼저 만들자. 아래는 제안이며 마이그레이션을 실행한 결과가 아니다.

| 논리 엔터티 | 최소 열과 관계 | 기존 구조 대응 |
|---|---|---|
| Source | source_id, 기관, 공식 URL, 수집 범위 | `data_source`, provider |
| Capture | capture_id, source_id, run_id, fetched_at, MIME, 바이트·텍스트 해시, 저장 위치, 상태 | `collection_run`, `raw_document`, `document_version` |
| Notice | notice_id, source_id, 원천 ID, 회차 ID, record_kind | `opportunity` |
| NoticeVersion | version_id, notice_id, capture_id, 이전 버전, 제목, 기간과 정밀도, review_status | `opportunity_version`, `document_version_id` 연결 |
| RuleSet | rule_set_id, version_id, 계약·파서 버전, root_id, source_coverage, normalization_coverage, 승인 상태 | 버전별 조건집 계약 추가 또는 기존 버전 열 보강 |
| RuleNode | node_id, rule_set_id, parent_id, position, node_kind, role, code, operator, typed_value, qualifiers, normalization_status | `eligibility_rule_group`, `eligibility_rule`, `criteria_definition` |
| Evidence | evidence_id, capture_id, 인용, 위치, evidence_origin, 해시 | `evidence_span` 및 연결 자료 |
| DemoEvaluation | fixture_id, fixture_version, 불변 profile_fixture_json, version_id, rule_set_id, evaluator_version, comparison_mode, query_as_of, 입력 해시, 노드 결과와 원인 | 가상 학생 고정 fixture. 실제 학생을 저장하지 않음 |

관계는 `Source → Capture → Evidence`, `Notice → NoticeVersion → RuleSet → RuleNode`, `NoticeVersion → Capture`, `RuleNode ↔ Evidence`, `DemoEvaluation → NoticeVersion + RuleSet`이다. 조건이 없는 공고도 원본 버전을 찾을 수 있어야 한다. 조건 하나가 본문과 참조 규정 두 근거를 가질 수 있으므로 조건과 근거는 다대다 연결을 허용한다. 가상 학생 입력 JSON과 그 버전을 보존해 입력 해시만 남는 일을 막는다.

타입 검사는 `code → 자료형·단위·허용 연산자` 사전으로 강제한다. 학교 코드에는 숫자 비교를 허용하지 않고, Boolean 값에는 임의 문자열을 허용하지 않는다. `between`은 하한≤상한과 양 끝 포함 여부를 검사한다. 트리는 순환이 없어야 하며 모든 노드는 같은 조건집에 속한다. 승인된 조건집은 수정하지 않고 새 버전으로 저장한다.

다음은 면학장학금 발췌를 구조화하는 **검토 대기 후보의 새 계약 예시**다. 원본 버전과 근거 위치를 확보하기 전에는 null을 유지한다. 실제 저장 데이터의 덮어쓰기나 승인된 JSON이 아니다.

```json
{
  "contract_version": "benefitlens-core-proposal-0.1",
  "source_record_id": "postech-policy:7ecc662821c23dec60c89c50",
  "notice_version_id": null,
  "review_status": "pending_review",
  "node_kind": "predicate",
  "role": "required",
  "code": "earned_credits",
  "operator": "gte",
  "typed_value": {"type": "decimal", "value": "10", "unit": "credit"},
  "qualifiers": {"basis": "unspecified", "term": null, "as_of": null},
  "evidence": {
    "source_url": "https://www.postech.ac.kr/kor/college-life/scholarship_types.do",
    "quote": "학자금지원구간 8구간 이내 10학점 이상 이수 백분위 77점(2.0) 이상",
    "locator": null,
    "observed_in": "unresolved_criteria_json",
    "raw_verified_in_this_review": false
  }
}
```

학기가 미정인 위 조건을 가상 학생의 직전학기 12학점과 곧바로 비교해 통과시키면 안 된다. 규정으로 적용 학기를 확인하거나 명시적인 비교 불가 원인을 반환해야 한다. 실수 오차를 피하려면 점수·학점은 DB numeric과 십진수 문자열 계약으로 계산한다.

## 9 LLM은 추출 후보를 만들고 조회는 조건으로 계산

```text
기존 공식 원문과 연결 자료
→ 구조 필드·표·규칙 파싱
→ 필요한 경우 LLM의 조건 후보·역할·트리·근거 제안
→ 인용 위치와 타입 검사
→ 사람의 표본 검토 및 승인
→ 불변 조건집과 DB 조회 뷰
→ 가상 프로필의 타입·시점 비교
→ 상태·원인·근거 반환
```

LLM 입력은 수집한 해당 문서와 연결된 규정이다. 출력에는 필드·역할·논리 경로·근거 인용·위치·미해석 이유를 요구한다. 기존 `extraction_candidate`의 `proposed_value`는 문자열이므로 제안 계약의 타입 있는 값과 트리로 넘어가는 검증 단계가 더 필요하다. 인용이 존재한다는 검사만으로 해석이 옳다고 승인하지 않는다.

조회할 때마다 LLM에 자격을 다시 묻지 않는다. 검토한 조건집과 학생의 해당 시점 정보를 규칙 엔진에서 비교한다. 같은 원문·파서·계약이면 후보를 재사용하고, 원문 또는 추출 계약이 바뀐 문서만 재처리하는 안을 검토하자. 모델명·프롬프트 버전·입출력 해시를 보존해 조건집의 출처를 추적한다. 이번 작업에서는 추가 LLM 추출이나 유료 실행을 하지 않았다.

## 10 제안 발표용 시연

**제안:** 공고·제도 표본 3개와 가상 학생 3명을 사용한 고정 데이터 시연을 먼저 만들자. 발표 시작에 “저장된 검토 대기 표본과 가상 프로필”이라고 표시하고, 원문→조건표→DB 관계→조회 결과→근거 펼치기 순서로 3분 정도에 보여준다.

첫 장면은 대학원 학생조교수당 석사과정의 저장된 기본조건 `POSTECH AND 석사 AND 재학`이다. 아래는 새 시연의 예상 결과이며 현재 엔진 실행 결과가 아니다.

| 가상 학생 | 학교 | 학위 | 학적 | 등록된 기본조건의 예상 결과 | 함께 표시할 상태 |
|---|---|---|---|---|---|
| A | POSTECH | 석사 | 재학 | 일치 | 자료 검토 대기 · 제도 안내 · 업무 및 지급기준 확인 |
| B | POSTECH | 학부 | 재학 | 불일치, 학위가 다름 | 자료 검토 대기 · 제도 안내 |
| C | POSTECH | 석사 | 미입력 | 확인 필요, 학적 입력 필요 | 자료 검토 대기 · 제도 안내 |

다음 장면에서 현대모비스의 OR 경로를 보여준다. 이야기 시연의 A·B·C 프로필은 그대로 두고, 학기·수료 경계는 별도 검증 fixture로 제시한다. 석사 2학기 재학생, 석사 4학기 학생, 박사이지만 Coursework 확인이 없는 사례의 예상 결과는 일치·불일치·확인 필요다. 이 공고의 저장 마감 `2026-09-29 10:00`은 자격 조건과 별도로 표시하며, 현재 접수 중이라고 시연하지 않는다.

마지막은 면학장학금이다. 구간 8과 9, 이수학점 10과 9.5의 경계값을 비교하되 적용 학기·기준이 미확인인 실제 표본에서는 **전체 결과 확인 필요가 남는 모습**을 보여준다. 숫자 연산만 보여줄 때에는 학기와 기준을 명시한 합성 조건집을 따로 표시한다. “계속지원 기준 미달” 구절을 임의 면제로 해석하지 않는다.

중복·변경 장면은 별도의 합성 시나리오로 추가할 수 있다. 같은 원문 해시를 두 번 가져오면 같은 버전을 재사용하고 실행 이력만 남긴다. 합성 수정본에서 구간 8을 7로 바꾸면 새 원본·조건집 버전을 만들고 해당 조건에 의존한 결과만 재계산한다. 과거 결과는 이전 버전을 계속 가리킨다. 실제 수정 이력이 확보된 경우에만 실제 사례로 바꾼다.

신청서 초안은 후속 연결 한 장으로 충분하다. 승인된 공식 문항과 공고 버전, 사용자가 확인한 경험을 이어 붙인다는 구조를 설명하자. 저장 요약의 공식 지원 문항 정본은 0건이므로 특정 실제 신청서에 맞는 초안이 완성됐다고 발표하지 않는다.

## 11 검증 방법과 완료 증거

**제안 검증:** 6개 진단 표본을 두 사람이 독립적으로 `필수·제외·우대·서류·의무`와 논리·근거 위치로 주석한다. 의견 차이를 보존한 뒤 공식 원문과 참조 규정으로 합의한다. 시연 완료 뒤 모집 공고 17건과 제도 안내 53건을 분리해 필드 빈도를 세는 것은 후속 작업이다. 표본을 고른 이유와 전체 분모를 함께 보고한다.

| 확인할 것 | 작은 검증 사례 | 완료 증거 |
|---|---|---|
| 필수조건 완전성 | 현대모비스 석사 재학 누락, 포스터 조건 미추출 | 검토본 대비 누락 목록. 누락이 있으면 그 공고의 전체 일치 표시를 보류 |
| 타입과 경계 | 구간 8/9, 학점 10/9.5, 점수 임계값과 만점 불일치 | 값·연산자·단위·학기를 고정한 기대 결과표 |
| AND/OR와 예외 | 박사 경로의 미입력 석사 학기, 특정 성적만 면제하는 합성 예외 | 노드별 3상태 결과와 실제 또는 합성 근거 |
| 미상 원인 | 미입력, 구간 산정 중, 시상식 날짜 없음, OCR 실패 | 각각 다른 원인 코드. 거짓 또는 참으로 강제 변환하지 않음 |
| 근거 정확성 | sourceText와 해당 원문 위치·정의 대조 | 직접 인용/문맥/규정의 구분, 인용 일치와 해석 일치 별도 기록 |
| 복제 일관성 | NC AI 선언 4개와 트리 잎 6개 비교 | 건수는 역할별 트리에서 계산. flat 목록과 트리의 ID·값 일치 |
| 승인 상태 | needs_review인 표본의 기본조건 일치 | 검토 대기 표시가 유지되고 승인 완료처럼 보이지 않음 |
| 버전 재현 | 같은 해시 재수집, 합성 수정 후 이전 결과 조회 | 공고·조건집·평가기 버전과 fixture로 동일 결과 재현 |

처음에는 통과율 하나를 높이기보다 **잘못된 전체 일치 건수, 누락 필수조건 수, 미상 원인별 건수, 근거 연결률**을 건수와 분모로 보고하자. 자동 비교를 많이 할 수 있는 공고만 고르면 품질을 과장하게 된다. 사용자 시간 절감·추천 정확도·초안 품질은 별도 측정 전에는 주장하지 않는다.

발표 준비의 완료 기준은 검토한 실제 표본 3개, 타입 있는 조건표, 최소 DB 관계, 가상 프로필 결과표와 원문 위치를 한 흐름에서 재현하는 것이다. 기본조건 전체 일치와 실제 자격·선발을 구분하고, 미해석·미확인 사례도 하나 이상 포함한다. 이번 문서 작성 자체를 이 시연의 구현 완료로 계산하지 않는다.
