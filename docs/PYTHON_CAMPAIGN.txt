BenefitLens Python 실행기 이관

무엇을 바꿨는가
에이전트가 배치를 선택하고 실행하던 방식을 SQLite 큐를 가진 단일 Python 프로세스로 바꿨다. 실행기는 등록 원천의 목록, 실제 상세 링크, 다음 페이지를 순회한다. 원문에서 확인한 검색 표현은 출처와 함께 사전에 추가한다. 반복해서 나온 표현과 URL은 다시 큐에 넣지 않는다.

실제 자동 처리
1. 현재 한국 날짜를 기준으로 목록과 상세를 확보한다.
2. 원문을 gzip으로 저장하고 원문 해시와 정확한 문장 위치를 보존한다.
3. 학생 지원 대상, 공개된 접수 기간, 실제 신청 링크를 기존 검증기에 통과시킨다.
4. 원천 ID와 신청 링크 중복을 제거한다. 같은 기관과 역할은 부모 후보로 묶는다.
5. 신규 변형, 기존 정본 재확인, 보류를 구분해 SQLite와 gzip JSONL에 기록한다.
6. 처리할 큐가 없으면 대기하고 다음 한국 날짜에 등록 원천을 다시 확인한다.

중단과 복구
실행 중 종료되어도 큐가 남는다. 재시작하면 미완료 작업을 복구한다. 단일 실행 잠금으로 중복 실행을 막는다. 일반 통신 오류는 대기 후 최대 5회 시도한다. HTTP 429는 Retry-After를 지키며, 403과 로그인 요구는 원천 검토 대상으로 멈춘다. 다른 원천의 처리는 계속한다. 호스트별 요청 간격은 최소 2초다. 하루 신규 요청 10,000회와 저장 예산 5GiB를 둔다.

집계 기준
기존 정본은 4,859개 원천 변형, 1,613개 부모 후보다. 새 실행기의 기계 검증 통과를 독립 검토 완료나 실제 개인의 지원 자격 충족으로 올리지 않는다. 동일 기관과 유사 역할에 대한 최종 의미 중복 판단은 미확정이다. 5만 건 목표 달성을 선언하지 않는다.
AcademicWorks는 문서와 표 필드를 수집하지만, 학생 범위와 접수 여부, 공통 신청서의 의미를 검증할 전용 어댑터가 완성되기 전까지 보류한다. 수집했다고 승인 공고로 세지 않는다.

범위
활성 확장 구성은 원천 78개다. 저장소의 기본 구성은 55개다. 기존에 실제 응답을 확보했던 기업의 Workday 경로도 포함했다. 새 사이트의 URL이나 API 경로를 추측해서 추가하지 않는다. Python 실행기는 공고 수집과 규칙 검증을 담당한다. 작성 패턴 생성, 임의 사이트의 의미 해석, 운영 DB 반영은 이 실행기의 자동 처리 범위에 포함하지 않았다. 실행기 안에서 모델을 호출하지 않는다.

실행 방법
활성 확장 구성: /home/longnew/.cache/datasets/benefitlens/scale50k-20261109/python-campaign-v1/resume-20261112/expanded_config.json
서비스 상태: systemctl --user status benefitlens-campaign.service
서비스 중지: systemctl --user stop benefitlens-campaign.service
수동 실행: 저장소에서 /usr/bin/python3 tools/run_benefitlens_campaign.py run --config <활성 확장 구성 경로>
상세 상태: /usr/bin/python3 tools/run_benefitlens_campaign.py status --config <활성 확장 구성 경로>
제한 실행: run --max-jobs 20 또는 run --max-seconds 120
내보내기: /usr/bin/python3 tools/run_benefitlens_campaign.py export
의존성: requests, beautifulsoup4, lxml. 현재 /usr/bin/python3에 설치된 환경으로 검증했다.

상태 파일은 status.json, 큐는 frontier.sqlite, 로그는 runner.log이다. 사용자 세션의 임시 서비스로 실행하며 오류 종료 시 다시 시작한다. 운영체제 재부팅 후 자동 시작하도록 설치하지 않았다.

검증 결과
82개 테스트 통과. 실제 제한 실행의 기계 검증 결과 1개를 내보낸 뒤 원문과 접수 기간을 재검증했다. 해당 결과는 독립 검토 완료로 승격하지 않았다. 세 에이전트의 작업은 모두 종료했다.

2026-11-09 갱신: 원문 native ID 집합이 같은 반복 페이지는 중단한다. 상세 처리와 목록 순회에 3:1 우선순위를 두고 원천별 순환으로 상세 검증 지연을 방지한다.

2026-11-10 갱신: 하루 요청 한도에 도달하면 새 HTTP 요청을 한국 시간 자정까지 쉬고, 이미 확보한 당일 원문만 처리한다. 대기열 전체를 재시도 상태로 덮어쓰지 않는다. Workday 근무 형태와 공고 ID를 분리하며, 확인된 Varbi 신청 경로는 기관과 공고 ID로 중복을 비교한다. 신청 URL 원문은 보존한다.

2026-11-10 통합 인계: 에이전트의 당일 검토 파일을 `python3 tools/run_benefitlens_campaign_handoff.py --review <절대 경로>`로 넘긴다. 도구는 행 해시와 공식 원문을 확인하고, 정본과 과거 인계, 같은 배치의 신청 경로와 기관/역할을 대조한다. 당일 검증 인계는 verified-handoffs 아래에 고정 파일로 남으며 운영 DB에 쓰지 않는다. Jobbnorge는 새 요청 전 robots를 확인하고 목록, 본문, 마감 정보, 공개 신청 설정과 마감 표시 템플릿을 함께 검증한다. 모든 요청은 기존 공용 예산에 포함한다.

2026-11-12 갱신: 선택 설정 `focus_new_validatable_details`로 상세 처리 차례 대부분을 신규 상세와 전용 검증기가 있는 원천에 우선 배정한다. 이전 공고 재확인과 목록 순회에도 차례를 배정한다. `daily_request_limits_kst`에 따라 11월 12일만 12,000회로 조정했다. Jobbnorge robots는 텍스트 응답으로 확인하고, 같은 공식 호스트와 동일 공고 ID로 이동하는 공개 상세 주소만 한 번 따른다. 기존 요청 간격, robots 정책과 예산이 적용되며 원래 주소와 최종 주소를 보존한다. Workday의 지역별 접수 안내는 해당 지역 적용 근거를 확인해야 검증에 사용한다.
