# BenefitLens 팀 작업 기준

GitHub 저장소는 코드, 스키마와 발표 문서를 관리한다. 데이터 묶음은 별도 비공개 저장소로 전달하고 묶음의 manifest를 작업 기록에 연결한다.

## 변경을 어디에 넣는가

| 작업 | 변경 위치 | 확인 기준 |
|---|---|---|
| 새 출처 | `pipeline/config/`, 수집 모듈 | 공식 원문, 첨부와 실패 상태 확인 |
| 조건 추출 | 공고 스키마, 파서와 테스트 | 원문 인용, 값, 단위와 AND/OR 일치 |
| 경험과 패턴 | 경험 스키마와 프로그램 지식 | 프로그램, 회차와 사례 근거 연결 |
| DB 변경 | 새 SQL 마이그레이션 | 기존 데이터 보존, 빈 DB 구성 성공 |
| 화면 | `web/pipeline-demo/` 또는 별도 웹 앱 | 실제 사용하는 API와 저장소 명시 |
| 발표 | `proposal/중간발표/` | 계획과 실행 결과, 후보와 검토 수 구분 |

## 작업 단위

한 브랜치에서 하나의 수집, 스키마 또는 화면 문제를 다룬다. Pull request에는 변경 이유, 실행 명령, 사용한 데이터 묶음과 관측 결과를 쓴다. CI는 Python 오프라인 테스트와 빈 DB 마이그레이션을 검사한다. 웹 회귀 검증은 후속 과제로 남아 있다.

현재 우선순위는 광역 원장 원문의 구조화, 경험 후보의 프로그램별 패턴 정리, 추가 자격 판정 회귀 수정이다. 수집량 증가만으로 이 작업의 완료를 판단하지 않는다.

수집을 실행할 때는 원본 URL, 수집 시각과 해시를 남긴다. 접근 실패는 이유와 재시도 상태로 기록하며 로그인과 보안 제한을 우회하지 않는다. 스케줄러를 새로 등록하기 전에 기존 수집 작업과 DB 대상이 겹치는지 확인한다.

## 공개 전 확인

`.env`, DB 덤프, `pipeline/data/`와 `.local/`이 Git에서 제외됐는지 확인한다. 과거 테스트 표본과 문서에는 공개 원문, 작성자 이름과 개인 연구 정보가 남아 있을 수 있다. 공개 저장소로 push하기 전에 팀에서 원문 배포 권리와 개인 정보 공개 범위를 검토한다. 새 코드의 라이선스는 프로젝트 소유자가 정한다.
