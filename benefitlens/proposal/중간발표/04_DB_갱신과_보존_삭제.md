# 예제 10개의 DB 테이블과 처리 흐름

## 여러 계층이라는 말의 의미

크게 보면 모두 관계형 DB의 테이블이다. 원문, 처리 상태, 공고, 경험과 패턴을 갱신 단위와 연결 관계에 맞춰 나눴다. 별도의 여러 DB를 사용한다는 뜻은 아니다. PostgreSQL이 중심 저장소이며 수집 당시의 SQLite와 원문 파일은 로컬 보관 자료다.

## 현재 사용하는 핵심 구조

| 테이블 또는 파일 | 한 건의 단위 | 주요 내용 |
|---|---|---|
| `pipeline_document`와 로컬 원문 파일 | 원문 버전 | URL, 원본과 텍스트 해시, 파일 경로 |
| `pipeline_work_item` | 처리할 공고 후보 | 처리 상태와 사유 |
| `opportunities` | 공고 또는 제도 예제 | 프로그램, 회차, 조건, 혜택, 공식 문항과 출처 |
| `program_knowledge` | 프로그램 | 경험 사례 배열, 작성 패턴 배열과 추출 실행 기록 |
| `opportunity_revision` | 공고의 변경 버전 | 이전 내용과 해시 |

활성 표본 DB에는 공고 10행과 경험이 있는 프로그램 지식 3행을 넣는다. 원문 전문은 로컬 보관 파일에서 읽고 공개 표본에는 넣지 않는다.

사례 14개와 패턴은 현재 각각 독립 테이블이 아니라 `program_knowledge`의 JSONB 배열이다. 예를 들어 Google 행 안에 경험 7개와 여러 문항의 패턴이 들어간다. 사례별 검색과 버전 관리가 커지면 별도 `experience_case`, `writing_pattern` 테이블로 분리할 수 있다.

## 왜 나누는가

한 프로그램의 모집 회차가 바뀌어도 같은 경험 원문을 공고마다 복사하지 않기 위해 `program_id`로 연결한다. 원문 수정과 조건 추출, 패턴 재계산의 상태도 서로 달라 원문과 처리 상태를 공고 내용과 구분한다.

`opportunities.program_id`로 `program_knowledge.program_id`를 LEFT JOIN하면 사용자가 보는 하나의 공고 객체에 조건, 혜택, 경험과 패턴이 합쳐진다. 현재 이 연결은 DB 외래키가 아닌 애플리케이션 조회에 의존한다.

## 현재 배치

신규 수집은 중지했다. 기존 원문 → 공고의 조건 및 혜택 구조화 → 프로그램별 경험 전체 LLM 분석 → 근거 검사 → 표본과 DB 저장 순서다. 일반 기관 연구비와 교원 전용 사업은 활성 예제와 발표 범위에서 제외한다.

## 다시 실행하면 무엇이 바뀌는가

- 같은 예제는 기본키로 갱신하고 같은 내용을 중복 추가하지 않는다.
- 경험 원문과 프롬프트 해시가 같으면 LLM 추출 결과를 재사용한다.
- 원문이 바뀌면 새 입력 해시로 분석하고 모델과 문서 근거를 기록한다.
- 예전 대규모 자료는 보존 자료로 유지하고 현재 화면은 예제 10개만 조회한다.

공개 표본 DB는 55433 포트를 사용한다. 현재 로컬 서비스 5179도 이 표본 DB를 조회하도록 전환했다. 기존 단수형 `opportunity`와 광역 발견 원장은 과거 구현이며 현재 화면의 조회 대상이 아니다.
