# BenefitLens 과제 요구사항 충족 계획

기준일: 2026년 10월 12일. 이 문서는 제안 발표에서 설명할 설계와 최종 발표까지 확보할 실행 증거를 구분한다.

## 1. 과제는 무엇을 요구하는가?

[공식 강의자료](</home/longnew/Desktop/course_work/26-2 학기/데이터엔지니어링/1_overview.pdf>) 27쪽의 제안 요구사항은 “Ideation, data collection & preprocessing, DB management”다. 최종 요구사항은 “Develop a product that addresses a real-world problem”, “using a large-scale DB (with potential LLM integration)”다.

따라서 제안서는 문제, 수집, 전처리와 DB 운영을 설명하고, 최종에는 실제 DB를 사용하는 제품과 데이터 규모를 보여주는 구성으로 작성한다.

## 2. 우리 프로젝트는 어떻게 대응하는가?

> BenefitLens는 기관마다 흩어진 학생 지원 공고와 신청 자료를 수집해, 개인 조건으로 지원 기회를 찾고 실제 제출 문항에 맞춰 지원서 초안을 준비하는 데이터 기반 서비스다. 학교 출처는 POSTECH의 학교, 대학원과 학과별 공개 공고로 한정하고, 재단, 기업과 국가 지원 정보를 연결한다.

| 요구사항 | 우리 계획 | 충족을 보여줄 자료 |
|---|---|---|
| Ideation | 기회 탐색, 자격 확인과 기관별 문서 작성에 드는 반복 작업을 줄인다. | 한 사용자의 기존 탐색 과정과 제품 사용 과정 비교 |
| Data collection | 기관 게시판을 크롤링하고 공고에 연결된 안내와 첨부까지 수집한다. 허용된 통합 CSV와 API로 초기 색인을 보강한다. 텍스트 없는 이미지와 스캔 문서는 OCR로 읽는다. | 출처 목록, 실제 원문과 첨부, 실행 시각, 수집 성공 및 실패 기록 |
| Preprocessing | 사업과 모집 회차를 분리하고, 지원 자격, 제출 서류, 작성 문항과 선정 후 의무를 구분한다. 조건을 항목, 비교 연산자, 값, 단위와 논리 관계로 구조화한다. | 동일 공고의 원문 문장, 구조화 결과, 프로필별 판정 비교 |
| DB management | 기관→사업→모집 회차→문서 버전→조건 및 문항을 연결한다. 후기와 패턴도 관련 사업과 문항에 연결하고 출처와 이용 범위를 저장한다. | 스키마, 중복 제거 결과, 연결 질의와 변경 전후 이력 |
| Real-world product | 프로필 입력→후보와 판정 근거→신청 방법과 문항→참고 패턴→본인 경험에 근거한 초안을 한 흐름으로 제공한다. | 실제 DB를 조회하는 웹 데모와 신청 준비 결과 |

전처리에서 LLM은 원문에서 조건과 관계를 추출하는 데 활용한다. 예시 문장 `4.5 만점에 3.5 이상`은 `항목=GPA, 연산자=>=, 값=3.5, 만점=4.5`로 저장하고 원문 위치를 연결한다. 여러 조건의 AND와 OR도 보존한다. 만점이나 기관의 환산 기준을 잃은 채 숫자만 비교하지 않는다.

후기에서는 작성자의 경험, 준비 조언과 글의 전개 패턴을 분리한다. 실제 제출 원고, 준비 후기와 선정 후 활동 수기도 구분한다. 공식 공고가 자격 판정의 기준이고, 이용 허용된 사례는 작성 참고로 사용한다.

DB 갱신은 일 단위 변경 확인을 기본 계획으로 둔다. 새 자료는 적재하고 수정된 자료는 새 버전으로 연결한다. 내용이 같으면 기존 처리 결과를 재사용하며 실패한 수집은 재시도 기록을 남긴다. 출처별 이용 조건과 게시 특성에 따라 확인 주기를 조정한다.

## 3. 그렇다면 large-scale DB는 무엇으로 설명하는가?

규모 확보는 **통합 지원 정보의 초기 일괄 적재, 기관별 상세 공고와 공개 과거 회차의 보강, 관련 수기와 후기의 축적**으로 진행한다. 데모 사용자에게 맞는 공고만 수집하지 않고, 수집한 지원 정보를 조회 단계에서 프로필로 거른다.

현재 공개 공급원 조사에서 학자금 지원 정보 CSV 1913행과 청년정책 수천 건을 확인했다. 이는 공급원의 관측량이며 우리 DB의 고유 적재량은 아니다. 기존에 검토한 고유 지원 정보 2000~5000건은 잠정적인 수집 목표로 두고, 실제 적재와 중복 제거 후 달성량을 확인한다. [학자금 정보 카탈로그](https://www.data.go.kr/data/15028252/fileData.do), [청년정책 검색](https://www.youthcenter.go.kr/youthPolicy/ythPlcyTotalSearch)

최종 발표에서는 고유 사업 수, 모집 회차 수, 원문 문서 수, 이용 가능한 사례 수, 저장 용량과 주요 질의 실행 시간을 각각 보고한다. 조건 행, 문장 조각과 재수집 횟수를 독립 공고 수에 합산하지 않는다.

공식 교안에는 최소 건수가 없다. **수천 건 수준이 이 과목의 large-scale DB 요구에 충분한지는 아직 확인되지 않았다.** 제안 발표에서 데이터 단위, 확보 가능한 규모와 확장 경로를 제시하고 교수에게 인정 범위를 확인한다. 이후 확장 우선순위는 공개 과거 회차와 관련 작성 자료이며, 부족하면 서비스 범위와 추가 출처의 실현 가능성을 재검토한다.

## 5. 발표에서는 무엇을 보여주면 되는가?

1. **수집:** 공식 공고, 연결 안내와 첨부가 수집된 장면.
2. **전처리:** 공고 문장이 조건 구조와 작성 문항으로 바뀐 전후 비교.
3. **DB 관리:** 기관과 모집 회차의 연결, 동일 자료 재수집과 수정 공고의 처리 차이.
4. **규모:** 중복 제거 후 실제 데이터 집계와 조회 결과.
5. **제품:** 본인 프로필로 후보를 고르고 신청 요건, 참고 패턴과 초안을 확인하는 흐름.

제안 발표에서는 설계와 확보 가능한 출처, 대표 실행 예시를 제시한다. 최종 발표에서는 같은 항목을 실제 적재량, 갱신 로그, DB 질의와 작동하는 제품으로 증명한다.
