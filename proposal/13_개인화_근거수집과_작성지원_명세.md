# 개인화 근거 수집, 요구 역추론과 작성 지원 명세
버전: personalization-plan-v1. 기준일: 2026-11-04. 이 문서는 신규 기능의 제안 명세다. 현재 실행되는 기능과 구분하며, 명세 작성으로 구현 완료를 표시하지 않는다.

## 1. 문제 시나리오

학생이 관심 있는 지원이나 인턴십 공고를 찾았지만 내 조건에 맞는지, 어떤 자료를 제출해야 하는지 바로 판단하기 어렵다. 학생이 입력한 정보도 충분하지 않을 수 있다. 공식 공고와 첨부, 본인 문서와 공개 프로필에서 필요한 사실을 찾아 연결하고, 부족한 사실을 질문한 뒤 작성 준비로 이어져야 한다.

목표는 근거가 있는 지원 여부 검토와 준비다. 정보를 발견하고 조건을 충족하는 것, 기관의 예외 승인과 최종 선정은 구분한다.

## 2. 명확화할 현재 문제와 근거

현재 [조건 판정](../web/pipeline-demo/match.mjs)은 이미 채운 프로필 필드를 비교한다. 필요한 사용자 사실을 역으로 도출하거나 공개 검색으로 보강하는 경로는 없다. [API 명세](중간발표/05_추론_API와_데모_검증.md)의 현재 설명은 “현재 서버에 개인화 초안을 생성하는 POST API는 없다.”다.

[경험 추출 코드](../pipeline/src/data_platform/writing_patterns.py)의 현재 지침은 “결과 라벨만으로 글의 우열을 결정하지 않는다.”다. 선정과 미선정 비교, 사례와 인용 연결은 있으나 명시적인 주의점 규칙과 사용자 사실을 연결한 초안은 신규 계약이 필요하다.

이 명세는 원문을 보존하고, 추출 또는 추론한 주장을 후보로 기록하고, 사용 가능한 사실과 부족한 정보를 구분하는 과정을 시스템의 산출물로 정의한다.

## 3. 처리 순서와 단계별 산출물

| 단계 | 입력과 처리 | 반드시 남길 산출물 |
| --- | --- | --- |
| A 요구 분해 | 공고, FAQ, 양식에서 자격, 심사 기준, 서류, 활동과 문항 분리 | requirement와 근거, 적용 시점 및 회차 |
| B 필요 사실 도출 | 각 requirement를 판정하거나 작성할 필드 찾기 | field, 용도, 필요한 시점, 확보 경로와 질문 |
| C 자료 확보 | 사용자 문서, 공개 프로필 검색, 공고에 연결된 서류 탐색 | 출처별 원문 버전, 역할과 주체 연결, 성공/실패 |
| D 사실 후보 구성 | 직접 추출, 규칙 계산, 의미 추론과 사용자 응답 | fact의 값, 방법, 근거, 확인 상태와 사용 가능 여부 |
| E 충돌과 결측 해소 | 서로 다른 시점과 사람의 기록 분리, 결정에 필요한 질문 우선 | 상충 기록과 채택 이유, 남은 질문 |
| F 적합성 검토 | 확인된 사실을 요구와 연결 | 자격, 실무적 적합성과 준비 상태를 분리한 결과 |
| G 작성 지침 도출 | 공식 문항과 사례의 관찰, 장점과 주의점 연결 | guidance_rule과 적용 범위, 필요한 본인 사실 |
| H 초안 계획과 생성 | 사용할 사실과 지침을 문항 슬롯에 배치 | draft_slot, 부족한 사실, 초안과 주장별 근거 |

역추론은 B와 D로 나눈다. B는 요구에서 필요한 사실을 역으로 찾는 작업이고, D는 자료에서 상태나 경험의 후보를 추론하는 작업이다. 의미 추론의 결론을 바로 확정 사실로 바꾸지 않는다.

## 4. 요구에서 필요한 정보를 역으로 찾는 규칙

requirement에는 criterion_id, kind, field와 연산 및 값, 적용 시점, 논리 경로, 예외와 evidence_ids를 둔다. kind는 eligibility, selection_criterion, application_document, activity, writing_prompt다.

해석 상태는 candidate, reviewed, ambiguous다. 기준 자체가 모호하거나 아직 검토되지 않았으면 자격의 확정 충족 또는 불충족으로 내리지 않는다. 필드 사전에 없는 요건도 원문과 함께 검토 대상으로 남긴다.

| 공고의 요구 | 필요한 사실 또는 자료 | 확보 방법과 결측 처리 |
| --- | --- | --- |
| 박사 재학 | 학위와 학적, 적용 시점의 상태 | 입력 또는 재학증명서. 공개 프로필은 후보이며 시점 확인 |
| 교과 수료 또는 대부분 이수 | 수료 여부나 이수 사실, 기관의 기준과 적용 시점 | 성적표와 학교 기준, 사용자 확인. 대부분을 임의의 비율로 환산하지 않음 |
| 특정 연구 분야 | 논문과 프로젝트의 주제, 본인 역할 | 공개 논문과 프로젝트에서 주제 후보 도출, 본인 역할 추가 확인 |
| 추천서와 2쪽 제안서 | 추천인 확보, 공식 문항과 분량 | 공고와 양식 해석, 준비 질문과 문서 확보 |
| 대면 인턴십 수행 | 수행 시기와 장소, 학생의 가능 여부 | 활동 의무와 일정 분리, 사용자에게 확인 |
| 본인의 연구 기여 서술 | 본인 행동, 결과와 근거 | 개인 자료에서 후보를 찾고 사용자 확인, 없으면 질문 |

field가 이미 확인돼 있으면 반복 질문하지 않는다. 같은 값도 적용 시점이 다르거나 충돌하면 다시 확인한다. 심사 기준은 글의 준비에 사용하며 자격 충족의 수치 점수로 바꾸지 않는다.

## 5. 개인 정보 보강과 동일인 확인

입력은 사용자가 지정한 이름과 소속, 공개 프로필 URL 또는 ORCID, 이미 확인한 사실과 제공한 문서다. 검색할 공개 식별 단서를 이용해 Google 등 검색 공급자로 공개 프로필, 논문, 프로젝트를 찾는 기능을 설계한다. 전체 성적표나 비공개 사실을 검색 질의에 넣지 않는다.

처음 일치한 이름을 자동으로 사용자의 이력에 합치지 않는다. 사용자가 지정한 프로필 식별자, 소속과 연구 이력 등으로 주체를 연결하며 이름만 같으면 ambiguous다. 연결 상태는 unverified, confirmed, ambiguous, rejected다.

검색 결과 발췌는 발견 단서다. 실제 페이지의 본문과 URL, 수집 시각과 해시, 인용을 확보해 후보 사실을 만든다. 접근 실패는 사실 부재와 구분한다.

- 공개 기록의 제목, 연도와 저자 관계는 동일인 연결과 출처가 확인되면 원문에 기록된 사실로 사용할 수 있다.
- 논문 제목의 연구 분야 해석은 semantic_inference 후보로 둔다.
- 논문 저자라는 이유로 특정 설계나 실험을 본인이 수행했다고 확정하지 않는다. 본인 기여는 사용자 확인이 필요하다.
- 연령, 국적, 소득과 가족관계를 이름이나 사진, 연구 이력으로 추정하지 않는다. 필요한 조건이면 해당 사실을 직접 확인할 자료나 응답을 받는다.

현재 프로필은 브라우저에서 비교한다. 신규 검색 기능을 구현할 때는 요청에 필요한 공개 검색 단서의 전송과 결과 저장 범위를 화면에 명시하고, 개인 자료를 공고용 공개 표본과 분리한다. 이 명세 단계에서 실제 사람을 검색하지 않았다.

## 6. 사실의 상태와 추론 이력

fact에는 fact_id, field, value, derivation_type, review_status, evidence_ids, derived_from_fact_ids, eligible_for_final_use와 적용 시점 at, 확인 기준일 as_of를 둔다. 원문에는 주체, 자료 역할, 보관 시점과 버전이 있어야 한다.

| 방법 | 예 | 사용 규칙 |
| --- | --- | --- |
| source_extract | 증명서에서 학위, 논문에서 제목 추출 | 정확한 주체와 시점, 문장 의미 확인 후 accepted |
| rule_derived | 입학 월과 기준일에서 경과 월 계산 | 계산 규칙과 부모 사실 보존. 경과 월을 수료 여부로 대체하지 않음 |
| semantic_inference | 연구 주제나 경험 역할 해석 | candidate. 검색과 질문에 활용하고 최종 자격과 개인 사실 서술에는 사용하지 않음 |
| user_confirmed | 본인이 수행한 작업과 결과 확인 | 응답을 근거 기록으로 연결하고 기존 후보와 이력 보존 |

review_status는 candidate, accepted, conflicted, rejected, missing이다. accepted가 아니면 eligible_for_final_use는 false다. semantic_inference도 false다. 사용자가 확인하면 그 확인을 근거로 새로운 user_confirmed 사실을 만들고 후보에서의 계보를 남긴다.

여러 소스의 값이 다르면 날짜와 자료 역할을 먼저 비교한다. 과거 소속과 현재 소속은 동시에 보존할 수 있다. 같은 시점의 충돌은 임의 평균이나 마지막 응답으로 덮지 않고 conflicted로 둔다. 사용자 확인은 발급 문서의 진위 검증과 구분한다.

확인된 과거 사실도 현재나 미래 시점의 조건을 자동 충족시키지 않는다. at가 다른 사실은 해당 시점의 추가 근거를 찾거나 질문한다. 동일인 연결이 모호한 공개 자료는 최종 사실로 채택하지 않고 동일인 확인 질문에만 사용한다.

## 7. 공고와 관련 서류의 확보

공고가 요구하는 자료를 다음과 같이 구분한다.

| artifact_kind | 예 | 시스템이 해야 할 일 |
| --- | --- | --- |
| official_blank_form | 기관 지원서 양식 | 공식 공고의 첨부와 연결 경로에서 해당 회차 파일 확보 |
| official_guideline | 작성 안내, FAQ와 문항 | 공식 본문과 PDF 등에서 문항, 분량과 제출 규칙 추출 |
| user_issued_record | 재학증명서, 성적증명서 | 필요한 문서와 발급 경로 안내, 사용자 제공 자료 처리 |
| user_authored_material | CV, 연구계획서와 경험 메모 | 본인 파일에서 사실 후보 추출, 현재 문항에 맞춰 준비 |
| reference_example | 공개 제출문, 후기와 인터뷰 | 프로그램과 사례, 자료 역할과 결과 확인 수준을 분리 |

자료 탐색은 선택한 공고의 공식 링크와 첨부에서 시작해 기관의 안내와 지정 신청 포털을 따라간다. 후보 링크의 역할과 출처를 확인한 뒤 확보한다. 별도 인턴십의 공고와 펠로우십 연계 인턴십 의무를 구분한다.

resource는 requirement_id, artifact_kind, resolution_status, download_url과 evidence_ids를 갖고 프로그램과 회차에 연결된다. found, not_found, access_restricted, not_provided, stale, needs_user_provided를 구분한다.

found는 파일이나 본문을 실제로 확보하고 회차와 역할을 확인한 상태다. not_found는 정한 탐색 범위에서 찾지 못한 것이며 존재하지 않는다는 결론이 아니다. not_provided는 공식 안내가 자유 양식 등으로 별도 양식을 제공하지 않음을 확인했을 때만 쓴다. 인증이 필요한 개인 문서는 공개 검색으로 대신 확보했다고 표시하지 않는다.

과거 회차 서류는 참고 상태로 보존한다. 현재 공식 양식 자리에 몰래 대체하지 않는다. 내려받지 못한 자료도 필요한 이유, 공식 경로와 다음 행동을 결과에 남긴다.

## 8. 적합성을 세 축으로 반환

- **자격:** 각 criterion의 satisfied, not_satisfied, unknown, exception_review와 사용한 사실 및 원문. 기본 일치와 최종 선정은 분리한다.
- **실무적 적합성:** 장소, 시기, 활동 의무와 사용자 선호 또는 가능 여부의 일치와 미확인. 자격 조건과 합치지 않는다.
- **작성 준비:** 공식 서류와 문항, 확보한 본인 사실, 부족한 근거와 질문.

연구 분야 유사성은 별도 참고 판단이다. 근거 없는 종합 적합도 점수나 합격 확률을 만들지 않는다. 결과에는 기준일과 입력 버전, 어떤 사실을 더 알면 결론이 바뀌는지 포함한다.

## 9. 선정 여부와 독립적인 작성 지침

guidance_rule은 guidance_kind, observation, observation_scope, scope_limit, suggested_action, evidence_ids, required_user_fields, transfer_scope와 causal_success_claim을 갖는다. guidance_kind는 structure, strengthen, avoid, question이다.

basis는 official_constraint, text_observation, author_reflection으로 구분한다. 경험이 없으면 공식 문항에서 직접 작성 체크 항목을 만들 수 있으며 이때 case_id는 null이다. 실제 경험에서 얻은 패턴으로 표시하지 않는다.

과거 자료는 작성 지원용으로 보존한다. 과거 공고와 공식 양식에서 당시 문항, 제출 요건과 평가 관점을 추출하고, 공개 지원서와 후기 및 인터뷰에서 전개 방식, 준비 과정과 작성자의 회고를 추출한다. 당시 공고와 실제 작성물은 각각 문서 역할을 기록해 연결한다.

같은 프로그램의 과거 자료를 현재 문항에 적용할 때는 학위, 요구 문항, 분량과 평가 기준의 변경을 대조한다. 원천 회차와 대상 회차, 인용 위치를 남기고 기존 적재 스키마의 scope_status를 historical_transfer로 기록한다. 다른 프로그램의 자료는 cross_program 또는 general 범위에서 적용 가능성을 검토한다. 현재 공식 문항에서 요구하는 본인 경험을 질문한 뒤 초안 슬롯에 배치한다.

선정 결과는 사례의 outcome_status로 별도 기록한다. selected, not_selected, unknown 모두 구성 관찰의 입력이 될 수 있다. 미선정이라는 라벨만으로 avoid를 만들지 않는다.

- 구조: 문제, 본인 행동, 결과와 계획의 배치 등 관찰 가능한 전개.
- 보강점: 공식 문항이 요구하는데 공개된 범위에서 부족한 정보와 다음 질문.
- 주의점: 근거 없는 수치나 본인 역할 불명확 등 실제 구절과 요구를 대조한 관찰.
- 작성자 회고: 작성자가 말한 반성은 작성자의 해석으로 귀속하고 실제 심사 이유와 구분.

인용이 있다는 검사와 그 인용이 지침을 뒷받침한다는 검토를 나눈다. 일부 발췌에서 결과가 보이지 않는다면 해당 공개 부분의 관찰로 한정하고 지원서 전체의 누락이라고 단정하지 않는다.

다른 프로그램의 사례는 transfer_scope를 cross_program 또는 general로 표시하고 현재 문항에 맞는지 별도로 검토한다. 해당 프로그램의 선정 패턴으로 표시하지 않는다. 모든 지침의 causal_success_claim은 false다.

## 10. 초안 슬롯과 최종 출력

문항별 draft_slot에 prompt_id, 사용할 guidance_ids, accepted인 fact_ids, missing_fields와 draft_text를 둔다.

타인 사례는 구조와 검토 질문에 쓰고 개인 성과를 채우는 근거로 쓰지 않는다. 추정한 주제만으로 실제 연구 결과나 본인 기여를 생성하지 않는다. 필요한 사실이 없으면 질문이나 명시적 빈칸을 남긴다.

최종 화면은 다음을 함께 보여준다.
1. 공고의 혜택과 회차, 원문과 확인 시점.
2. 세 축의 적합성 결과와 근거, 예외와 미확인.
3. 필요한 공식 서류, 확보 상태와 발급 또는 제출 경로.
4. 사용자 사실 후보와 확인할 항목.
5. 적용한 작성 지침, 문항별 개요와 초기 초안, 남은 질문.

## 11. DB와 기존 구현의 연결

다음 저장 구조는 제안이며 실제 테이블을 생성하지 않았다. PostgreSQL과 JSONB를 유지한다.

| 저장 단위 | 제안 저장 위치 | 기존 구현과 관계 |
| --- | --- | --- |
| 원문 버전과 근거 | 기존 문서 보관층의 주체, 역할과 접근 범위 확장 | pipeline_document와 개인 문서의 분리 필요 |
| 개인의 사실 스냅샷 | personal_context의 facts와 identity_bindings JSONB | 현재 브라우저 프로필에는 후보와 이력 저장 없음 |
| 요구별 서류 해석과 확보 상태 | application_resource | 현재 prompts와 requirements에서 확장 |
| 판정 스냅샷 | assessment_snapshot | 공고/프로필/규칙 버전으로 재현 |
| 작성 지침 | program_knowledge.payload의 guidance_rules | 현재 writing_pattern과 observations를 유지하며 확장 |

accepted 사실을 현재 비교 함수의 flat profile로 바꾸는 어댑터가 필요하다. 그때 GPA의 만점과 범위, 미래 시점과 예외를 보존한다. 같은 입력과 버전의 캐시와 갱신을 분리한다.

## 12. 최소 완료 장면과 평가

최소 한 프로그램과 합성 사용자에서 공식 공고 → 필요한 사실 → 개인 문서와 공개 검색 후보 → 동일인 및 사실 확인 → 서류 확보 → 세 축 판정 → 지침과 초안 슬롯을 연결한다. 기존 10개 제한과 광역 수집 중지는 유지한다.

평가에는 아래 사례가 반드시 포함된다.
- 동명이인 공개 기록은 최종 사용자 사실에 합쳐지지 않음.
- PhD candidate라는 표현만으로 수료를 확정하지 않음.
- 공식 양식 미발견과 제공하지 않음, 개인 발급 문서가 구분됨.
- 과거 회차 양식이 현재 양식으로 표시되지 않음.
- 미선정 또는 결과 미상 글에서도 근거 있는 구조와 주의점을 추출함.
- 불완전한 공개 자료로 전체 지원서의 결함이나 탈락 원인을 단정하지 않음.
- 확인 전 사실과 타인의 사실이 사용자 초안의 확정 주장으로 들어가지 않음.

주체 연결 정확도, 사실 후보와 accepted 사실의 정밀도, 결정적 사실 누락, 서류 회차/역할 정확도, 지침 근거 타당성과 초안 사실 추가를 독립 정답으로 측정한다. 기계 계약 검사는 의미 정확도를 대신하지 않는다.

## 13. 기계 계약과 현재 경계

[JSON Schema](../docs/specs/personalization-plan.schema.json)와 [합성 예시](../evaluation/spec_examples/personalization-plan.synthetic.json)는 미래 입출력 계약이다. 기존 HTTP API나 현재 DB의 저장 형식을 교체하지 않았다.

단계별 요청과 응답, 부분 실패 상태는 [제안 API](../docs/specs/README.md)에 정의한다. 계획, 문서 입력, 공개 검색, 서류 탐색, 사실 확인과 초안 생성 요청을 분리한다.

개인 공개 검색, 개인 문서 업로드, 요구 기반 정보 계획기, 서류 확보 상태 관리, 명시적 guidance_rules와 슬롯별 초안 생성은 신규 구현 대상이다. 현재의 조건 판정과 원문 인용 및 사례 연결 검증은 재사용할 기반이다.

[최종 완료 계약](12_최종_완료_계약과_결과물_형식.md), [평가 규약](07_평가_계획과_채점_기준.md), [마일스톤](BenefitLens_최종발표까지_마일스톤_계획.md)에 이 확장 경로를 함께 반영한다.
