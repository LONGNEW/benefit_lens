# 데이터엔지니어링 팀프로젝트 제안서

## BenefitLens: 지원 기회를 찾고 내 경험으로 신청 초안을 만드는 학생 워크벤치

### 한 문장 제안

BenefitLens는 여러 기관에 흩어진 지원 기회를 공식 데이터로 수집하고 개인 조건으로 걸러, 사용자가 같은 경험을 기관별 요구에 맞춰 반복해서 재작성하는 비용을 줄이는 근거 기반 지원 준비 파이프라인이다. 장학금은 이를 검증하는 첫 도메인이다.

1단계는 **지원 기회를 근거와 함께 찾는 것**, 2단계는 **자기 경험으로 첫 초안을 만드는 것**이다. 모든 지원을 안다고 주장하지 않으며 합격을 예측하거나 타인의 문장과 경험을 쓰지 않는다.

## 1. 무엇을 해결하는가

지원자는 기회를 찾고 신청할 때마다 `기회 탐색 → 자격 확인 → 기관별 문항 해석 → 자기 경험 재구성`을 반복한다. 첫 검증 도메인인 장학금만 보아도 학교, 재단, 기업과 국가의 사이트를 각각 방문해야 한다. 같은 조건도 재학생, 학부생, 거주 지역, 학자금지원구간처럼 다르게 쓰이고, 공고마다 마감과 증빙 기준이 다르다. 검색 결과를 읽은 뒤에도 사용자는 다음을 다시 판단해야 한다.

- 내 조건과 맞는가?
- 무엇이 부족하거나 확인되지 않았는가?
- 현재 접수 중인가?
- 어느 문장을 근거로 한 판단인가?
- 지난번 확인 뒤 조건이나 마감이 바뀌었는가?
- 선택한 공고는 어떤 문항과 증거를 요구하는가?
- 내 경험 중 무엇을 어느 순서로 써야 하는가?

BenefitLens는 이 판단 과정을 네 출처 범주에 한정해 연결한다. 사용자는 학교, 재단, 기업과 국가의 지원을 한 화면에서 비교한다.

기회를 찾은 뒤에도 빈 지원서 앞에서 다시 검색해야 한다. 공식 양식과 평가 기준, 공개 수기, 후기와 작성 팁은 흩어져 있다. BenefitLens는 문장을 가져오지 않고 **문항, 문단 역할, 필요한 근거와 점검 질문**을 추출한다. 사용자가 경험 질문에 답하면 확인된 답만으로 개요와 초안을 만든다.

검증 가설은 두 개다.

> 네 범주의 공식 사이트를 직접 확인하는 방식과 비교했을 때, 등록 출처의 범위와 최신성을 공개하는 통합 보드가 사용자가 검토할 공고와 부족한 조건을 더 빠르고 정확하게 찾게 하는가?

> 빈 신청서나 일반적인 대화형 AI만 사용하는 방식과 비교했을 때, 공고 문항에 맞춘 구조화 질문과 근거 계보가 사용자의 사실을 꾸며내지 않으면서 더 완전하고 수정하기 쉬운 첫 초안을 만드는가?

## 2. 범위 계약

첫 버전의 대상은 **POSTECH 재학생**이다. 장학금을 첫 검증 도메인으로 삼고 아래 네 출처 범주를 둔다.

| 범주 | 포함 범위 | 초기 출처 예시 |
|---|---|---|
| 학교 | 공개 접근 가능한 교내 장학 제도와 학생 대상 금전 지원 | POSTECH 장학 안내, 공개 공지 |
| 재단 | 공개 모집 회차와 신청 문항을 확인할 수 있는 장학재단 | 포스코청암재단, 삼성꿈장학재단 |
| 기업 | 기업 또는 기업 연계 기관이 운영하는 공개 지원 프로그램 | 기업 사회공헌 및 인재 지원 프로그램 |
| 국가 | 공공 API 또는 공식 포털에서 확인 가능한 국가 지원 | 한국장학재단 학자금지원정보와 공식 공고 |

학교 출처는 **POSTECH 한 곳**으로 고정한다. 재단, 기업과 국가는 각 3개씩 연결해 총 10개 출처를 목표로 한다. 범주별 한 출처의 골드 세트를 먼저 완성하고, 수집 안정성과 운영 비용을 통과한 경우에만 학교를 제외한 세 범주를 각 4개까지 늘린다. 과거 전체를 모으지 않고 현재 접수 중인 공고와 최근 12개월의 변경 이력만 다룬다.

한국장학재단의 대학생 학자금지원정보는 월간 파일로 제공되지만, 제공기관도 전체 기관의 정보를 포함하지 않으며 모집 시기와 방법이 바뀔 수 있다고 밝힌다. 이 한계는 서비스의 수집 범위 공개가 선택 기능이 아니라 핵심 기능이어야 한다는 실제 근거다.

인증이 필요한 교내 게시판은 권한과 재배포 허용 범위를 확인하기 전까지 자동 수집하지 않는다. 공개 교내 출처만으로 신청 시점 정보가 부족하면 학교 계층은 제도 목록으로 표시하고, 실제 모집 여부는 원문 확인이 필요하다고 명시한다. 이 문제를 숨긴 채 신청 가능으로 판정하지 않는다.

## 3. 전체 공지를 알 수 없는데도 가치가 있는가

이 서비스의 가치는 완전한 목록이 아니라 **정해진 중요 출처를 반복해서 확인하고, 조건과 변경을 같은 방식으로 비교하는 것**에 있다. 사용자가 매번 네 범주의 사이트를 방문하고 서로 다른 표현을 해석하는 비용을 줄인다.

다만 공고가 검색되지 않았다는 이유로 “받을 수 있는 지원이 없다”고 말하면 안 된다. 결과 화면에는 항상 다음 범위 정보를 붙인다.

- 등록 출처 이름과 공식 원문 링크
- 출처별 마지막 수집 성공 시각
- 최근 실행 상태: 정상, 지연, 파서 실패, 접근 불가
- 검색에 포함된 게시일 범위
- 마지막 사람 검토 시각
- “이 결과는 아래 등록 출처에서 확인한 범위입니다. 다른 기관과 비공개 공지는 포함되지 않을 수 있습니다.”라는 고정 안내

검색 결과가 없을 때는 **“등록 출처의 정상 수집 구간에서 조건에 맞는 공고를 찾지 못했습니다”**라고 표시한다. 하나라도 수집에 실패했다면 **“일부 출처를 확인하지 못해 결과가 불완전합니다”**라고 먼저 보여준다.

## 4. 단순 검색과 무엇이 다른가

알림 서비스는 새 글의 존재를 알려주지만, BenefitLens는 공고를 공통 구조로 바꾸고 사용자 상태와 대조한다. 핵심은 추천 알고리즘보다 다음 네 가지다.

1. 학교, 재단, 기업과 국가 공고의 서로 다른 필드를 하나의 조건 스키마로 정규화한다.
2. 동일 사업의 수정 공고와 모집 회차를 연결해 어떤 조건이 바뀌었는지 보여준다.
3. 판정마다 조건 값, 근거 문장, 원문 버전과 수집 시각을 연결한다.
4. 공고 목록과 별개로 출처의 수집 성공 여부를 저장해 결과의 범위를 설명한다.

서비스는 선발 가능성을 예측하지 않는다. `신청 가능`이라는 단정도 쓰지 않고 다음 상태를 사용한다.

| 상태 | 의미 |
|---|---|
| 조건상 검토 가능 | 입력한 값과 구조화한 필수 조건이 맞지만 기관 심사와 미수집 조건이 남을 수 있음 |
| 명시 조건 미충족 | 확인된 필수 조건 중 하나 이상이 맞지 않음 |
| 추가 확인 필요 | 사용자 입력, 공고 표현 또는 중복 수혜 규정이 불완전함 |
| 기간 종료 | 확인된 접수 기간이 지남 |

각 결과에는 “공식 신청 전 원문 확인 필요”와 신청 링크를 제공한다.

### 4.1 선택한 기회에서 초안까지

2단계는 장학금 전체의 만능 자기소개서가 아니라 **한 공고의 실제 신청 문항을 완성하는 보조 도구**다. 첫 구현은 공개 양식과 충분한 작성 자료를 확보한 신청 유형 하나로 제한한다.

자료는 용도와 권리에 따라 나눈다.

| 등급 | 자료 | 제품에서의 사용 |
|---|---|---|
| A | 기관의 공식 신청 양식, 문항, 평가 기준과 작성 안내 | 요구 문항과 필수 내용의 기준 |
| B | 이용 조건이 패턴 분석을 허용하는 수상 수기나 사례 | 문단 역할과 근거 배치 패턴의 집계 |
| C | 이용 허락을 확인하지 못한 공개 후기와 팁 | 출처 탐색과 링크 안내에만 사용하며 패턴 말뭉치에서는 제외 |
| 제외 | 유료 자료, 비공개 커뮤니티, 작성자나 이용 조건이 불명확한 전문 | 수집과 생성에 사용하지 않음 |

공개 웹페이지도 저작권과 이용 조건을 확인한다. 원문 전문을 노출하지 않으며, 허용이 불명확하면 URL, 제목과 작성 시점만 보존한다. 수상작 바꿔쓰기와 허위 경험 생성은 제공하지 않는다.

추출하는 것은 합격 문장이 아니라 다음의 **서술 역할**이다.

- 지원 동기와 문제 상황
- 사용자가 실제로 한 선택과 행동
- 행동을 뒷받침하는 구체적 근거
- 결과와 배운 점
- 앞으로의 계획과 해당 지원의 연결

서비스 흐름은 `공고 선택 → 공식 문항 확인 → 경험 질문 → 답변 확인 → 개요와 초안 생성 → 미확인 주장과 누락 문항 점검`이다. 각 주장은 사용자 답변과 연결한다. 입력에 없는 수상, 성과, 가족 사정, 활동과 수치는 만들지 않고 추가 질문으로 남긴다.

“후기의 공통 패턴이 정말 합격 공식인가?”라는 반문에는 아니라고 답한다. 공개 후기는 생존자 편향이 있고 탈락 사례와 심사 맥락이 부족하므로 선발 원인을 증명하지 못한다. 패턴은 글의 완결성과 가독성을 돕는 후보 구조일 뿐이며, 공식 문항과 평가 기준을 항상 우선한다.

## 5. 데이터 모델과 계보

핵심 테이블은 다음과 같다.

- `source_scope`: 계층, 기관, URL, 수집 구간, 지원 형식, 갱신 주기, 이용 조건, 포함 게시판과 제외 범위
- `crawl_run`: 시작과 종료 시각, 접속과 파싱 상태, 발견 문서 수, 미처리 문서 수와 오류 원인
- `raw_document`: 원문 위치, 해시, 수집 시각, 이용 조건과 보존 정책
- `opportunity`: 사업의 지속 식별자, 운영기관, 계층과 지원 형태
- `opportunity_version`: 모집 회차, 게시일, 접수 기간과 변경 내용
- `eligibility_rule`: 학적, 거주지, 연령, 성적, 소득, 중복 제한, AND와 OR 구조
- `evidence`: 구조화한 값과 이를 뒷받침하는 원문 문장과 위치
- `profile_snapshot`: 사용자가 판정에 동의해 입력한 최소 정보와 시점
- `evaluation`: 판정 상태, 사용한 공고 버전, 규칙 버전과 판정 시각
- `writing_source`: 공식 양식, 공개 수기와 팁의 출처, 이용 조건, 허용된 저장과 변환 범위
- `application_prompt`: 공고 버전별 신청 문항, 글자 수, 요구 근거와 평가 항목
- `narrative_pattern`: 이용이 허용된 자료에서 얻은 동기, 행동, 근거, 결과, 배운 점과 향후 계획 태그와 산출 근거
- `template_version`: 적용 대상 문항, 질문 순서, 포함 규칙과 사용한 작성 자료 버전
- `experience_fact`: 사용자가 직접 입력하고 확인한 경험 사실과 선택적 증빙
- `draft_version`: 사용한 문항, 템플릿, 사용자 사실과 생성 시점
- `claim_provenance`: 초안의 각 주장과 이를 뒷받침하는 사용자 답변 또는 미확인 상태

`source_scope`와 `crawl_run`이 없다면 서비스는 누락과 실제 부재를 구분할 수 없다. 2단계에서도 문항과 템플릿의 버전이 없으면 이전 양식에 맞춘 글이 생성될 수 있다. 양식이 바뀌면 관련 템플릿을 자동 수정하지 않고 재검토 필요로 막는다. `claim_provenance`는 사용자가 말한 내용임을 보일 뿐 사실의 진위를 보증하지 않으므로 제출 전 사용자 확인을 요구한다.

## 6. 파이프라인

```text
등록 출처 수집
→ 원본과 수집 실행 상태 저장
→ 새 문서와 변경 문서 식별
→ 기간, 금액, 대상과 조건 후보 추출
→ 공통 스키마로 정규화
→ 규칙 검사와 표본 사람 검토
→ 공고 버전과 근거 연결
→ 사용자 프로필과 조건 대조
→ 결과와 수집 범위 상태를 함께 질의

선택한 공고의 신청 양식과 작성 자료 수집
→ 권리와 용도 등급 기록
→ 문항, 글자 수와 평가 항목 정규화
→ 허용된 자료에서 서술 역할을 주석하고 패턴 집계
→ 공고 버전에 맞는 질문 템플릿 생성
→ 사용자 경험 답변과 초안의 주장 연결
→ 미확인 주장, 누락 문항과 출처 유사성 점검
```

구현은 Python 수집기, 스케줄러, 원본 파일 저장소와 PostgreSQL을 기본으로 한다. 관계형 테이블과 연결 테이블로 충분하므로 그래프 DB는 쓰지 않는다. LLM은 조건과 문단 역할의 후보 추출, 사용자 질문과 초안 생성에 사용한다. 자격 상태는 검증된 구조와 규칙으로 계산하고, 초안의 개인 사실은 확인된 사용자 입력만 허용한다.

수집은 하루 한 번 실행하고 HTML과 텍스트 추출이 가능한 PDF 한 종류까지만 지원한다. 접속 성공과 문서 처리 성공을 분리해 기록한다. 이전 수집 결과를 보여줄 때는 오래된 자료임을 표시하고, 새로 발견했지만 처리하지 못한 문서 수를 숨기지 않는다.

공개 자료라도 출처별 이용 조건을 기록한다. 화면에는 공고 전문을 복제하기보다 필요한 구조화 값, 짧은 근거 문장과 공식 원문 링크를 제공한다. 자동 수집과 재배포가 허용되지 않거나 불명확한 출처는 제외하거나 기관 허가를 받는다.

## 7. 한 학기 구현 범위

### 반드시 만든다

- POSTECH 한 곳과 재단, 기업, 국가 각 3개로 구성한 목표 10개 공식 출처의 실행 상태 대시보드
- 현재 공고와 최근 12개월 버전을 보존하는 DB
- 학적, 거주지, 연령, 성적, 소득, 기간을 다루는 조건 모델
- 조건상 검토 가능, 명시 조건 미충족, 추가 확인 필요, 기간 종료 판정
- 판정 근거와 원문 연결
- 학교, 재단, 기업, 국가 필터와 수집 범위 안내
- 한 조건을 바꾸었을 때 달라지는 결과 비교
- 프로필 최소 수집, 보관 기간 설정과 삭제 기능
- 신청 유형 하나의 공식 문항과 글자 수 정규화
- 권리 감사에서 통과한 작성 자료 5건에서 10건과 버전이 있는 서술 패턴
- 사용자의 경험을 묻는 구조화 인터뷰, 개요와 첫 초안 생성
- 초안의 주장별 사용자 근거, 미확인 사실과 미완성 문항 표시

### 이번 학기에는 만들지 않는다

- 전국 모든 대학과 지자체로의 확장
- 초중고생, 대학원생, 구직자와 직장인 지원
- 자동 신청, 합격 확률, 지원금 총액 보장
- 모든 장학금에 통하는 자기소개서와 합격 문장 추천
- 타인의 수기 전문 제공, 문장 바꿔쓰기와 허위 경험 생성
- 은행과 학사시스템 연결
- 사용자가 알지 못하는 개인 정보를 추론하는 개인화
- 조건을 완료하면 미래 기회가 연쇄적으로 열린다는 장기 로드맵

마인드맵과 퀘스트 표현은 후속 확장으로 남긴다. 첫 버전의 최종 행동은 **오늘 검토할 공고 하나를 고르고, 공식 문항에 맞추어 자기 경험으로 작성한 검토 가능한 첫 초안을 얻는 것**이다.

## 8. 평가 계획

모든 평가는 전체 지원 생태계가 아니라 등록 출처와 고정된 기간 안에서 수행한다.

### 데이터 품질

- 같은 기간의 등록 출처를 사람이 직접 확인해 기준 공고 목록을 만든다.
- 기준 목록 대비 공고 발견 재현율과 중복 제거 정확도를 측정한다.
- 사람이 검토한 공고 50건에서 기간, 금액, 대상과 조건 추출 정확도를 측정한다.
- 프로필과 공고 조합에서 상태별 정밀도와 재현율, 판정 보류율, 잘못된 `조건상 검토 가능` 판정률을 측정한다.
- 모든 판정이 정확한 원문 버전과 근거 문장으로 연결되는 비율을 측정한다.

### 사용자 가치

학생에게 “현재 검토할 공고 두 개와 각 공고에서 확인할 조건을 찾으라”는 과제를 준다. 네 범주의 공식 사이트를 직접 보는 방식과 BenefitLens를 쓰는 방식을 비교해 완료 시간, 놓친 공고 수, 조건 해석 오류 수를 측정한다. “새로운 지원을 몇 개 발견했는가”는 등록 출처 안에서만 보고한다.

2단계는 같은 신청 문항을 대상으로 빈 양식 또는 일반 대화형 AI와 BenefitLens를 비교한다. 문항 요구사항 충족률, 사용자가 제공하지 않은 개인 사실, 사용자 확인이 연결된 주장 비율, 첫 초안 시간과 수정량을 측정한다. 이용이 허용돼 보존한 자료에 대해서만 문장 유사성을 검사한다. 장학금 합격률은 성과 지표로 쓰지 않는다.

### 시스템과 운영

- 변경 공고가 들어온 뒤 영향받는 판정만 다시 계산되는지 확인한다.
- 수집 실패를 정상 결과로 오인하지 않고 UI에 반영하는지 시험한다.
- 운영 상한은 저장 공간 20GB, 서버 월 3만원, 수동 검토 주 60분으로 둔다.

## 9. 중단 기준과 위험

첫 2주 안에 아래 중 하나가 발생하면 범위를 다시 줄이거나 주제를 중단한다.

- 학교, 재단, 기업, 국가 중 핵심 범주에서 합법적이고 반복 가능한 공개 수집 경로를 하나 이상 확보하지 못함
- 범주별 골드 출처에서 공고의 게시일, 접수 기간과 원문 링크를 안정적으로 얻지 못함
- 표본 30건 중 20건 이상에서 핵심 자격을 명시적 규칙으로 표현할 수 없음
- 강한 기준점인 공식 사이트 통합 북마크와 수작업 조건표보다 사용자 과제 시간이 30퍼센트 이상 줄지 않음
- 수동 검토 시간이 주 60분을 넘음
- 신청 유형 하나에서도 공식 문항을 확보하지 못하거나, 권리 감사 뒤 사용할 수 있는 작성 자료가 5건 미만임
- 초안 평가에서 사용자 입력에 없는 개인 사실이 반복적으로 생성되거나 출처 표현과 과도하게 유사한 문장이 통제되지 않음

교내 핵심 공지가 인증 영역에만 존재할 가능성이 가장 큰 위험이다. 이 경우 비공개 게시판을 우회 수집하지 않는다. 공식 협조로 접근 범위를 정하거나, 학교 계층의 기능을 공개 제도 안내와 원문 연결로 낮춘다.

후기 자료의 권리가 불명확하면 2단계를 버리지 않고 **공식 신청 양식과 평가 기준만 이용한 구조화 인터뷰**로 축소한다. 이 대안도 문항 정규화, 템플릿 버전, 사용자 사실과 초안의 계보를 유지하므로 데이터 엔지니어링 가치는 남는다.

## 10. 수업 채점 기준과의 연결

| 기준 | 보여줄 증거 |
|---|---|
| Novelty | 제한된 출처의 조건 정규화와 범위 공개를, 공고별 문항 정규화와 사용자 경험 기반 초안으로 연결 |
| Impact | 기회 탐색 시간과 오류, 첫 초안의 완결성, 근거 없는 주장, 작성 시간과 수정량을 비교 측정 |
| Technology | 두 종류의 출처 수집, 엔터티 연결, 조건과 서술 역할 스키마, 증분 갱신, 템플릿 버전, 판정과 초안 계보 구현 |
| Presentation | 수집 실패와 공고 변경이 탐색 결과, 신청 문항, 질문 템플릿과 초안 점검에 이어지는 전체 흐름 시연 |

대규모라는 말은 문서 수만으로 주장하지 않는다. 실제 문서, 공고 버전, 조건, 근거와 수집 실행 로그의 규모를 각각 보고하고, 수업에서 요구하는 데이터 규모는 교수자에게 별도로 확인한다.

## 11. 최종 시연

1. 대시보드에서 학교, 재단, 기업과 국가의 등록 출처와 마지막 수집 상태를 확인한다.
2. 한 출처의 파서 실패를 보여주고 결과가 불완전하다는 경고가 나타나는지 확인한다.
3. 학생 프로필을 입력하면 네 가지 상태로 공고가 나뉜다.
4. 한 공고를 열어 판정 근거 문장과 공식 원문을 확인한다.
5. 학점이나 거주지 값을 바꾸면 영향받는 결과만 다시 계산된다.
6. 수정 공고가 들어오면 이전 버전과 달라진 조건과 재판정 내역이 나타난다.
7. 검토 가능한 공고 하나를 선택해 공식 신청 문항과 요구 내용을 불러온다.
8. 사용자가 자신의 경험 질문에 답하면 개요와 첫 초안이 만들어진다.
9. 초안의 각 주장을 사용자 답변까지 추적하고, 입력에 없는 사실과 미완성 문항을 표시한다.

이 시연은 **“우리가 어디까지 확인했고, 왜 이 공고를 검토해야 하며, 어떤 사용자 사실로 초안이 만들어졌는지 재현 가능하게 설명한다”**는 약속을 보여준다.
