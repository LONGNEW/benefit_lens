# BenefitLens 내부 DB와 파이프라인 기틀 초안

현재 구현 계약은 [데이터 추출 계약](../docs/데이터_추출_계약.md), 실행 증거는 [실행 기준](../docs/실행_기준.md)을 따른다. 아래는 초기 설계이며 사업 회차 통합, 서버 판정 저장, 승인 템플릿과 LLM 주장 계보는 목표다.

> 상태: 구현 완료 보고가 아니라 팀 합의를 위한 상세 설계 초안이다. 기존 제안서에서 확정한 범위는 **기준**, 이 문서가 보강한 구조는 **제안**, 실제 출처를 확인해야 정할 값은 **미정**으로 구분한다.

## 1. 왜 화면보다 이 기틀을 먼저 정하는가

현재 범위의 사용자는 POSTECH 재학생이다. 사용자는 학교, 재단, 기업과 국가의 등록 출처에서 검토할 공고와 근거를 확인하고 하나를 선택한 뒤, 그 공고의 공식 문항에 자신의 경험을 답해 첫 초안을 얻는다.

수업은 제안 단계에서 수집, 전처리와 DB 관리를, 최종 단계에서 종단 데이터 제품을 요구한다. 과거 발표도 실제 데이터, 아키텍처, DB, 실행 증거, 시연과 정량 결과를 함께 제시했다. 따라서 지금 필요한 것은 화면 목록이 아니라 **입력이 어떤 근거와 버전을 거쳐 판정과 초안이 되는지 재현하는 내부 계약**이다. 이 계약이 없으면 0건, 수정 공고와 생성문을 신뢰할 수 없다.

## 2. 실패에서 저장 구조를 도출한다

| 예상 실패 | 사용자에게 생기는 문제 | 필요한 구조와 통제 |
|---|---|---|
| 등록 범위와 실행 상태가 없음 | 미수집을 기회 없음으로 오해 | `source_scope`, `crawl_run`, 미처리 문서 수 |
| 수정 공고가 현재값을 덮어씀 | 과거 판정과 근거를 재현하지 못함 | 불변 `raw_document`, `opportunity_version`, `evidence` |
| 입력 누락을 거짓으로 처리 | 실제로 확인이 필요한 사용자를 탈락시킴 | 프로필 스냅샷, 참, 거짓, 미상의 3값 규칙 |
| LLM이 자격을 직접 판정 | 같은 입력의 결과가 달라지고 근거가 흐려짐 | 검증된 규칙 엔진, 판정 및 규칙 버전 |
| 바뀐 양식에 예전 템플릿 사용 | 다른 문항에 맞춘 초안을 제공 | 문항과 템플릿 버전, 재검토 차단 상태 |
| 생성문과 사용자 답변이 분리 | 근거 없는 개인 사실을 찾지 못함 | `experience_fact`, `draft_version`, `claim_provenance` |
| 권리 미확인 자료를 분석 | 저작권과 재배포 위험 | 자료별 권리 등급과 허용 작업 게이트 |

## 3. 전체 구조와 저장소의 역할

```text
공식 출처와 허용된 작성 자료
→ 출처 및 권리 등록부
→ 수집 어댑터와 실행 로그
→ 권리상 저장이 허용된 불변 원본 파일 저장소
→ 파싱, 변경 탐지, 정규화, 품질 검사
→ PostgreSQL의 공고, 조건, 문항, 템플릿 버전
→ 규칙 기반 개인 조건 대조
→ 경험 질문, 사용자 확인, 초안 생성
→ 판정 근거와 초안 주장 계보를 포함한 조회 결과
```

저장이 허용된 원문과 첨부만 파일 저장소에 보존하고 PostgreSQL에는 위치, 해시, 권리, 버전과 정규화 값을 둔다. 링크 안내만 허용된 자료는 URL과 메타데이터만 남기고, 제외 자료는 수집하거나 저장하지 않는다. 사용자 개인정보는 별도 스키마와 최소 권한으로 분리한다. 첫 구현의 **제안**은 Python 배치와 스케줄러다. 대표 출처에서 실행 시간, 실패율, 재처리 시간과 비용을 측정해 유지 여부를 판단한다. Kafka, 그래프 DB와 벡터 DB는 현재 필수 질의로 필요성이 확인되지 않아 초기 범위에서 제외한다.

**초기 제안 범위**는 학교, 재단, 기업과 국가에서 각 1개 골드 출처로 시작한다. 학교는 POSTECH으로 고정한다. 일 단위 수집과 외부 출처 확장은 목표다. 초기 HTML과 PDF 처리에서 이미지 OCR, HWP와 HWPX로 구현을 확장했다. 작성은 신청 유형 하나와 권리 감사를 통과한 자료 5건에서 10건으로 제한한다.

## 4. 최소 DB 계약

먼저 이름의 혼동을 줄인다. `opportunity`는 여러 회차에 걸친 사업, `opportunity_version`은 특정 회차와 정정본이다. `application_prompt`는 LLM 지시문이 아니라 신청서의 공식 문항이다. `evaluation`은 프로젝트 성능 평가가 아니라 한 프로필의 자격 판정 기록이다. `template_version`은 문항별 질문과 포함 규칙의 승인본이며, `claim_provenance`는 초안 주장과 사용자 답변을 잇는 연결이다.

| 영역 | 핵심 테이블 | 반드시 답해야 하는 질문 |
|---|---|---|
| 출처와 원본 | `source_scope`, `crawl_run`, `raw_document`, `parse_run` | 어디를 언제 확인했고, 어느 파서로 무엇이 실패하거나 바뀌었는가? |
| 공고와 조건 | `opportunity`, `opportunity_version`, `eligibility_rule`, `evidence` | 어느 회차의 어떤 원문이 이 조건을 만들었는가? |
| 개인 판정 | `profile_snapshot`, `profile_attribute`, `evaluation`, `evaluation_rule_result` | 어떤 사용자 입력과 규칙 버전으로 이 상태가 나왔는가? |
| 문항과 템플릿 | `writing_source`, `application_prompt`, `narrative_pattern`, `template_version` | 어느 양식과 허용 자료가 질문 순서를 만들었는가? |
| 경험과 초안 | `experience_fact`, `generation_run`, `draft_version`, `draft_claim`, `claim_provenance`, `draft_issue` | 어떤 입력과 생성 실행이 각 주장과 누락을 만들었는가? |
| 운영과 품질 | `quality_check`, `review_task` | 어떤 검사를 통과했고 무엇을 사람이 확인해야 하는가? |

기존 엔터티에 `parse_run`, `profile_attribute`, `evaluation_rule_result`, `generation_run`, `draft_claim`, `draft_issue`, `quality_check`, `review_task`를 **제안**으로 추가한다.

필수 FK 흐름은 `source_scope 1:N crawl_run 1:N raw_document 1:N parse_run`, `parse_run N:M opportunity_version via evidence`, `opportunity 1:N opportunity_version 1:N eligibility_rule`, `profile_snapshot + opportunity_version 1:N evaluation`, `opportunity_version 1:N application_prompt`, `template_version + experience_fact 1:N generation_run 1:1 draft_version`, `draft_claim N:M experience_fact 또는 evidence`다.

다음 제약은 구현 전에 고정한다.

- `opportunity`는 지속되는 사업의 식별자이고 `opportunity_version`은 특정 모집 회차와 정정본이다. 버전 행은 갱신하지 않고 새 행을 추가한다.
- `raw_document`는 `source_id + 원천 식별자 + content_hash`로 중복을 막고 `storage_mode=blob|metadata_only|external_pointer`를 기록한다. 삭제 의무가 생기면 원본을 지우고 삭제 상태와 시각만 남긴다.
- 모든 정규화 값과 원자 조건의 `evidence`는 원본과 `parse_run`, 페이지 또는 문자 위치를 참조한다.
- 날짜만 있으면 `date`로 보존하고 원문에 시각과 시간대가 있을 때만 `timestamp`와 UTC를 만든다. 금액은 통화, 학점은 원점수와 만점, 연령은 기준일, 거주지는 행정 단위를 함께 둔다.
- `eligibility_rule`은 AND, OR, 예외를 트리로 표현하며 원문에 없는 값을 대입하지 않는다.
- `evaluation`은 프로필, 공고, 규칙 엔진 버전을 고정한다. `generation_run`은 모델, 생성 프롬프트 템플릿, 매개변수와 입출력 해시를 남기며 `draft_version`은 이를 참조한다.
- 개인 정보는 가명 사용자 키로 연결하고 보관 기한, 동의 버전, 삭제 시각을 기록한다. 원본 공고와 개인 답변의 접근 권한을 분리한다.

## 5. 파이프라인 A: 수집과 전처리

| 단계 | 출력 | 통과 기준과 실패 처리 |
|---|---|---|
| 1. 출처 등록 | 범위, 갱신 주기, 접근 방식, 권리 등급 | 인증 우회가 필요하거나 이용 범위가 불명확하면 본문 수집을 시작하지 않음 |
| 2. 원본 수집 | 실행 로그, 원본, 응답 메타데이터 | 접속 성공과 문서 처리 성공을 분리하고 0건, 건수 급변, 구조 변경을 경고 |
| 3. 변경 탐지 | 신규, 동일, 수정 후보 | 해시와 원천 식별자를 함께 사용하고 정정공고를 단순 중복으로 삭제하지 않음 |
| 4. 후보 추출 | 기간, 금액, 대상, 조건과 문항 후보 | LLM은 후보와 원문 위치를 반환하며 모델 점수는 검토 우선순위용 원시 신호로만 저장 |
| 5. 정규화 | 공통 타입과 조건 트리 | 날짜, 단위, 만점, 경계 포함 여부, AND와 OR가 모호하면 `review_task` 생성 |
| 6. 품질 검사 | 검사 결과와 검토 상태 | 실패 행은 판정 대상에서 격리하되 미처리 수, 실패 단계, 마지막 정상 시각과 불완전 경고는 조회 결과에 포함 |
| 7. 버전 공개 | 승인된 공고와 문항 버전 | 이전 버전을 보존하고 영향받는 판정과 템플릿만 갱신 대상으로 표시 |

상태 전이는 출처 `active → paused|blocked|retired`, 실행 `queued → running → succeeded|partial|failed → retrying`, 후보 버전 `extracted → review_pending → approved|rejected → published → superseded`로 제한한다. 공개 전환은 한 사업 회차에 현재 버전 하나만 남도록 트랜잭션으로 처리하고 실패 재시도는 마지막 정상 버전을 덮어쓰지 않는다.

원본을 먼저 보존한 뒤 변환하는 이유는 파서나 규칙이 틀렸을 때 새 버전으로 재처리하기 위해서다. 결측 자격을 평균값이나 추정값으로 채우지 않고, `명시 없음`, `사용자 미입력`, `파싱 실패`를 구분한다. 하루 한 번 수집을 기본으로 하되 실제 갱신 간격을 측정한 뒤 조정한다.

## 6. 파이프라인 B: 사용자 개인화

첫 버전의 개인화는 추천 모델이 아니라 **사용자가 명시적으로 제공한 최소 정보와 공고 규칙의 대조**다. 학적, 거주지, 연령, 성적, 소득과 판정 시점만 수집하며 사용자가 제공하지 않은 민감 정보를 추론하지 않는다.

수집 상태, 기간 상태, 자격 상태를 하나의 값으로 섞지 않는다. 원천 접근은 성공과 접근 불가, 파싱은 성공과 일부 실패와 실패, 신선도는 정상과 지연과 미상으로 각각 저장한다. 이 세 축에서 결과 완전성을 완전, 부분, 사용 불가로 파생한다. 그다음 기간을 접수 전, 접수 중, 종료, 미상으로 계산한다. 접수 중인 공고의 조건 트리는 다음처럼 평가한다.

- AND 묶음은 하나라도 거짓이면 거짓, 모두 참이면 참, 그 외에는 미상이다.
- OR 묶음은 하나라도 참이면 참, 모두 거짓이면 거짓, 그 외에는 미상이다.
- NOT은 참과 거짓만 뒤집고 미상은 유지한다. 명시적 제외 조건의 참은 기본 조건보다 우선한다.
- 명시 조건 하나가 거짓이면 `명시 조건 미충족`, 거짓은 없지만 미상이 있으면 `추가 확인 필요`, 모두 참이면 `조건상 검토 가능`이다.
- 기간이 끝났으면 화면 상태는 `기간 종료`로 표시하되 당시의 자격 계산은 별도로 보존한다.
- 접수 전 공고는 저장하되 사용자 결과에 포함할지와 어떤 이름으로 표시할지는 아직 정하지 않는다.
- 부분 수집 경고는 자격 상태를 덮어쓰지 않고 결과 전체의 완전성 경고로 제공한다.

화면 우선순위는 다음과 같다. 수집 실패는 상단 경고와 마지막 정상 수집 시각으로 보이고 새 판정을 만들지 않는다. 정상 수집된 공고가 종료 상태면 `기간 종료`를 주 상태로 보인다. 접수 중이면 자격의 거짓, 미상, 참 순서로 각각 `명시 조건 미충족`, `추가 확인 필요`, `조건상 검토 가능`을 표시한다. 접수 전과 기간 미상의 주 상태는 **미정**이다.

출력은 사용한 프로필 값, 조건별 결과, 부족한 입력, 명시된 증빙, 근거, 공고 버전과 마지막 정상 수집 시각을 함께 반환한다. 과거 평가는 현재 프로필로 다시 쓰지 않고 당시 `profile_snapshot`과 함께 보존한다. 삭제 이후의 재현 범위는 10절의 미정 사항이다.

## 7. 파이프라인 C: 초안 제공

기존 제안서의 두 파이프라인을 이 문서에서는 수집과 전처리, 개인 판정, 초안 제공으로 나눴다. 세 단계의 실패 기준과 승인 주체가 다르기 때문이다. 사용자 흐름 전에 다음 내부 준비가 먼저 끝나야 한다.

```text
writing_source 등록
→ 권리 등급 확인
→ 공식 문항과 허용 사례의 서술 역할 주석
→ narrative_pattern 집계
→ template_version 초안
→ 사람 검토와 approved 전환
```

```text
공고 버전 선택
→ 공식 문항, 글자 수와 평가 기준 확정
→ 사용 가능한 템플릿 확인
→ 문항별 경험 질문
→ 사용자 답변을 사실 후보로 저장하고 사용자 확인
→ 확인된 사실로 개요와 초안 생성
→ 문장을 주장 단위로 분리하고 답변과 연결
→ 누락 문항, 무근거 주장, 길이와 유사성 검사
→ 사용자 수정과 최종 확인을 새 버전으로 저장
```

템플릿은 `draft`, `approved`, `review_required`, `retired` 상태를 가진다. 문항, 연결된 작성 자료나 주석이 바뀌거나 권리가 철회되면 관련 템플릿을 `review_required`로 바꾸고 생성에 사용하지 않는다. A등급은 공식 문항과 안내, B등급은 분석 허용 사례, C등급은 링크 안내만 가능한 자료다. 내용 처리에는 A와 B만 사용한다.

LLM은 후보 추출, 추가 질문, 개요와 문장화를 맡고 자격, 사실의 진위, 권리와 템플릿 승인은 맡지 않는다. 구조화 결과의 주장은 개인 사실, 사업 사실, 해석, 연결 문장으로 나눈다. 각각 `experience_fact`, `evidence`나 `application_prompt`, 근거 주장과 사용자 확인에 연결하며 연결 문장에는 사실 검사를 적용하지 않는다. 근거의 존재, 소유권, 확인 상태와 의미 일치를 후처리하고 `auto_linked|reviewed|rejected`를 남긴다. 미지원 주장은 초안에서 경고하되 최종 확인을 차단한다. 사용자 확인은 본인 제공 내용이라는 뜻이지 외부 진위 검증이 아니다. 누락 요구, 글자 수 위반과 허용 자료 유사성도 `draft_issue`로 기록한다.

예를 들어 정정공고가 들어오면 새 원본과 새 공고 버전을 만들고 기존 판정은 보존한다. 변경된 조건으로 현재 판정만 다시 계산한다. 신청 문항도 바뀌었다면 기존 템플릿을 차단한다. 새 템플릿이 승인된 뒤 사용자가 답한 경험으로 초안을 만들고, 각 주장을 그 답변까지 연결한다. 이 한 흐름이 버전, 판정과 생성 계보를 함께 증명한다.

## 8. 계획된 완료 기준과 제출할 증거

아래 수치와 범위는 새 성과 주장이 아니라 통합 제안서와 평가 계획에서 가져온 **기준**이다. 실제 달성 여부는 구현 뒤 별도로 측정한다.

| 검증 대상 | 목표와 향후 남길 증거 |
|---|---|
| 데이터 감사 | 범주별 공고 후보 10건, 작성 자료 후보 15건의 접근, 형식과 권리 확인 |
| 개발 자료 | 공고 30건으로 규칙과 파서를 설계하고, 공고 10건과 작성 자료 5건 이상을 두 사람이 독립 주석 |
| 분리 평가 | 등록 출처와 고정 기간의 수작업 목록을 분모로, 미사용 공고 20건 이상과 작성 자료 3건 이상에서 품질 계산 |
| 품질 지표 | 발견과 필드 및 문항 추출, 상태 판정, 근거 연결, 주석자 일치도, 템플릿과 자료 버전 연결률 측정 |
| 초안 품질 | 허용 자료 5건에서 10건과 사용자 과제에서 문항 충족, 무근거 개인 사실, 계보, 시간과 수정량 측정 |
| 재현성 | 원본과 정규화 중복 0건, 판정의 멱등성, 과거 판정 재현과 버전별 재처리 로그를 목표로 함 |
| 안전 게이트 | 권리 미허용 자료와 재검토 템플릿 사용 0건, 경고 없는 미지원 주장 0건을 목표로 함 |
| 운영 가능성 | 저장량 20GB 이하, 서버 월 3만원 이하, 수동 검토 주 60분 이하, 실패 뒤 재시도와 복구 기록 |
| 사용자 가치 | 성인 학생 8명에서 12명의 교차 과제로 직접 사이트, 빈 양식 또는 일반 대화형 AI와 비교 |

발표에서는 기술 이름보다 다음 연결을 보여준다. 파서 실패가 범위 경고로 이어지고, 정정공고가 새 버전과 재판정으로 이어지며, 양식 변경이 템플릿 차단으로 이어지고, 사용자 답변이 초안 주장까지 추적되는 장면이다. 이는 Novelty에는 두 파이프라인의 연결, Impact에는 시간과 오류 감소, Technology에는 버전과 계보, Presentation에는 실패를 포함한 종단 시연으로 대응한다.

## 9. 축소와 중단 게이트

- 핵심 범주에서 합법적이고 반복 가능한 출처를 확보하지 못하거나 공식 문항을 얻지 못하면 범위를 축소한다.
- 범주별 골드 출처에서 게시일, 기간과 원문 링크를 안정적으로 얻지 못하거나 공고 30건 중 20건 이상을 규칙으로 표현하지 못하면 출처나 조건 범위를 줄인다.
- 기존 방식보다 탐색 시간이 30퍼센트 이상 줄지 않거나 수동 검토가 주 60분을 넘으면 조건 질의와 근거 설명만 남겨 가설을 다시 검토한다.
- 허용 작성 자료가 5건 미만이면 사례 패턴을 제거하고 공식 문항과 평가 기준만 쓰는 인터뷰로 축소한다.
- 근거 없는 개인 사실이나 과도한 출처 유사성을 통제하지 못하면 자연어 초안을 중단하고 개요만 제공하거나 해당 자료를 제거한다.

## 10. 구현 전에 끝내야 할 미정 사항

1. 범주별 골드 출처 4개, 신청 유형, 사용자 범위와 사업, 회차, 정정본의 동일성 규칙을 확정한다.
2. 접수 전과 기간 미상 공고의 표시 정책, 검토 담당자, 승인 이력과 처리 기한을 정한다.
3. 원본, 프로필과 초안의 보관 및 삭제, 삭제 뒤 허용할 익명 집계와 재현 범위를 정한다.
4. 외부 LLM 전송과 비식별화, 프롬프트 인젝션 방어, 접근 로그와 백업 기준을 정한다.
5. 파서의 사람 검토 전환, 주장 의미 일치 검토와 유사성 차단 기준을 표본으로 정한다.
6. 사용자가 초안을 수정한 뒤 주장 계보를 유지하는 편집 규칙을 정한다.
7. 품질 통과선과 수정량 계산 방식, 수업의 대규모 DB 규모를 평가 전에 확정한다.
8. `source_scope`와 `writing_source`의 공통 상위 출처 및 재시도 멱등성 키와 트랜잭션 경계를 정한다.
