# 최종 완료 계약과 결과물 형식
기준일: 2026-11-04. 현재 구현, 내부 목표와 수업 요구사항을 구분한다. 정확도와 완료 여부는 [평가 계획](07_평가_계획과_채점_기준.md)의 증거로 판정한다.

개인 문서와 공개 검색으로 사실을 보강하고, 공고가 요구하는 서류를 확보하며, 사례의 구조와 주의점을 초안에 연결하는 신규 기능은 [개인화 근거 수집 명세](13_개인화_근거수집과_작성지원_명세.md)를 따른다. 이 문서의 입력과 출력 계약을 확장하는 설계이며 현재 API의 구현 완료를 뜻하지 않는다.

## 1. 문제 시나리오와 제품 목표

학생이 자신의 학업과 연구에 관련된 지원과 인턴십 기회를 발견하고, 조건과 제약을 확인한 뒤 준비 여부를 결정한다. BenefitLens는 흩어진 공고와 경험을 원문 근거, 모집 회차와 조건의 적용 시점에 연결해 판단과 준비에 쓸 데이터로 만든다.

현재 범위는 학생 개인 대상 예제 10개다. 별도 인턴십 공고는 이 표본에 없다. NVIDIA의 인턴십은 펠로우십에 연결된 수행 요구사항이다. 이를 독립 인턴십 선발이나 인턴십 자격 확보로 표시하지 않는다. 독립 인턴십을 추가하려면 예제 교체 여부와 유형 스키마를 M0에서 결정하고 공식 공고를 확인한다. 신규 광역 수집은 재개하지 않는다.

## 2. 현재 상태와 최종 종료 기준

| 구간 | 현재 확인 상태 | 최종에 남길 산출물 | 종료 기준 |
| --- | --- | --- | --- |
| 저장 형식 | 11월 4일 공개 표본 10/10 계약 검사 통과, 조건 트리 9개와 잎 36개 | 고정 입력, 스키마와 검사 결과 | 모든 입력의 형식 검사 통과, 누락 조건은 미상으로 유지 |
| 원문과 구조화 | Google, NVIDIA, Gates, 관정 4개는 원문 해시 연결. 6개는 요약 표본 | 공고별 공식 원문과 추출 결과, 오류표 | 평가 대상 전부 원문 검토 가능. 실패한 자료는 검증 분모와 건수에서 별도 표시 |
| 의미 정확도 | 독립 정답 주석 없음 | 정답표, 버전 고정 추출 결과, 오류 건수와 지표 | 07 문서의 내부 목표 충족 또는 실패 범위와 수정 결정 공개 |
| 개인 조건 비교 | 과거 10월 18일 11개 기능 시나리오 통과 | 정답과 독립적으로 만든 프로필별 판정과 근거 | 기본 조건, 추가 확인, 모집 상태와 활동 요구를 구분 |
| 개인 사실과 서류 보강 | 공개 검색, 개인 문서 입력과 서류 확보 상태 관리는 미구현 | 근거가 있는 사실 후보, 확인 상태와 필요 서류, 적합성 세 축 | 한 프로그램에서 필요 사실 도출 → 자료 확보 → 확인 → 판정과 작성 슬롯 연결 |
| 작성 지원 | 3프로그램, 14사례, 25문서 분석과 17패턴, 빈칸 개요 | 문항별 질문, 사용자 사실, 개요와 초기 문장 초안 | 한 프로그램의 실제 문항에서 사용자 사실만 반영한 초안 생성과 분량 검사 |
| 갱신 | 정기 실행 미완료 | 일 단위 실행 로그, 변경 전후, 실패와 복구 기록 | 7일 연속 관측, 동일 입력 재적재 불변, 통제된 수정 사례 반영 |
| 제품 실행 | 11월 4일 DB 조회 API는 HTTP 503 | DB 조회와 사용자 출력 시연, 복구 절차와 백업 영상 | 제출 환경에서 실제 조회와 대표 시나리오가 동작 |
| 규모 | 활성 예제 10개. 과거 검색 원문은 별도 보관 | 원천 문서와 고유 사업 및 회차별 수, 저장량, 질의 시간 | large-scale 인정 범위 확인과 해당 범위의 실제 집계 및 질의 증거 |

10/10과 11/11은 각각 형식과 과거 기능 검사다. 추출 정확도나 사용자 효과로 표기하지 않는다. 세부 결과는 [평가 파일 안내](../evaluation/final/README.md)를 따른다.

## 3. 학생에게 받을 입력

기본 입력은 학위와 재학 상태다. 기관, 학기, 국적, 수료 여부, GPA와 만점은 선택한 공고의 조건에 필요할 때 추가로 받는다. 모르는 값은 비워 두고 추가 확인 대상으로 둔다.

작성 입력은 공식 문항에 따라 연구 문제, 본인 기여, 실제 결과와 근거, 향후 계획 등 패턴의 required_inputs를 사용한다. 추천인과 활동 수행 가능 여부는 학생이 확인할 질문으로 제시한다.

재학증명서의 영어 명칭은 certificate of enrollment, 성적증명서는 academic transcript다. 개인 문서 입력과 사용자 공개 프로필 검색은 신규 구현 목표이며 현재 업로드와 검색 API는 없다. 요구에서 필요한 사실을 도출한 뒤 원문, 규칙 계산과 의미 추론을 구분해 후보로 저장한다. 확인된 필드는 재사용하고 부족하거나 충돌한 사실을 질문한다. 문서 진위 검증 완료라는 표시는 별도 검증 없이 사용하지 않는다.

## 4. 학생이 받아야 하는 공고 카드

| 화면 항목 | 현재 데이터 또는 함수 | 표시 규칙 |
| --- | --- | --- |
| 프로그램과 모집 회차 | program_id, round_id, title | 제도 안내와 모집 회차를 구분 |
| 기본 조건 | evaluateEligibility의 result와 trace | true는 기본 조건 일치, false는 불일치, null은 정보 부족 |
| 추가 조건과 예외 | additional_checks, evaluateAdditional | pass, fail, unknown, exception을 구분. invalid와 recorded는 충족으로 합치지 않음 |
| 모집 상태 | applicationState | open, closed, upcoming, rolling, unknown과 기준일을 함께 표시 |
| 혜택 | benefits | 종류, 금액과 통화, 최대/정액 여부, 기간과 지급 경로. 미기재 값은 채우지 않음 |
| 활동과 제출 요구 | requirements, application.prompts | 인턴십 수행과 추천서 등 의무를 기본 자격과 나눔 |
| 확인 근거 | source_refs | 공식 URL, 원문 구절과 위치, 보관 회차와 확인 시점 |
| 다음 행동 | 위 결과에서 도출 | 추가 정보 입력, 공식 문의, 경로 제외, 서류 준비를 구분 |

기본 조건만 일치한 카드를 최종 지원 가능이나 선정 확정으로 표시하지 않는다. 보관본의 날짜와 기준일은 화면에 보여준다.

현재 HTTP 응답은 상세 공고의 data, version_hash와 knowledge다. 조건 판정은 브라우저에서 수행한다. 이 표는 화면 계약이며 신규 서버 판정 API가 구현됐다는 뜻이 아니다.

## 5. 공통 저장 형식

기계 계약은 [opportunity.schema.json](../pipeline/schemas/opportunity.schema.json), 필드 사전은 [eligibility_fields.json](../pipeline/config/eligibility_fields.json)이다.

- 식별: opportunity_id, program_id, round_id.
- 자격: eligibility의 all, any, not과 field, op, value, at, evidence_ref. GPA는 scale, degree_scope, period_scope를 함께 보존.
- 혜택: benefits와 금액, 통화, 기간, amount_kind 및 근거.
- 지원 안내: application의 공식 URL, 날짜와 prompts.
- 추가 확인과 의무: additional_checks와 requirements.
- 추적: source_refs, extractor, extraction_status, resolution_status.

현재 category의 허용값은 scholarship, fellowship, admission_funding, other다. internship은 독립 유형으로 구현되지 않았다. 필드를 새로 제안하면 저장 스키마, 검증기, UI와 평가 지침을 같은 변경으로 갱신한다.

## 6. 작성 결과 형식

현재 knowledge는 프로그램별 사례와 writing_pattern을 제공한다. 각 패턴은 pattern_id, sections, required_inputs, supporting_case_ids와 원문 근거를 갖는다. 프로그램 연결이 없는 경험을 같은 프로그램의 사례로 섞지 않는다.

최종 목표의 문항별 출력은 다음 다섯 부분이다.
1. 공식 문항, 분량과 현재 모집 회차.
2. 사용한 패턴과 근거 사례, 적용한 이유.
3. 필요한 본인 사실과 부족한 입력 질문.
4. 본인 사실을 반영한 초기 초안.
5. 사용자 사실과 문항을 대응시킨 검토표, 남은 빈칸과 분량 검사.

한 프로그램의 실제 문항 1개 이상에서 이 연결을 완료한다. 나머지 프로그램이 개요만 제공하면 결과 수준을 표시한다. 패턴이 없는 프로그램은 공식 문항과 일반적인 준비 안내만 제공하며 해당 프로그램의 경험 패턴을 확보했다고 표시하지 않는다.

선정, 미선정과 결과 미상 사례에서도 원문에 근거한 구조, 보강점과 주의점을 guidance_rule로 만들 수 있다. 선정 결과와 관찰의 근거 수준, 전체 원고와 공개 발췌를 구분한다. 개인 사실은 accepted인 기록만 문장에 쓰고 타인의 사례는 구조와 질문에 활용한다. 세부 계약은 13 문서의 사실 상태, 서류 상태와 초안 슬롯을 따른다.

## 7. 제출 패키지의 내부 권장 형태

| 산출물 | 반드시 포함할 내용 |
| --- | --- |
| 실행 가능한 웹 제품 | 실제 DB 조회, 공고 카드, 추가 확인과 한 문항의 초기 초안 |
| 발표 자료 | 문제, 실제 원문과 판단 변화, 수집과 처리, DB 관계, 검증, 범위와 한계 |
| 코드와 실행 문서 | 환경, 입력 버전, 스키마, 실행 명령과 실패 복구 |
| 평가 폴더 | 표본 목록, 정답 주석, 고정 출력, 오류표, 지표, 실행 로그 |
| 데모 백업 | 같은 입력과 데이터 버전의 영상과 결과 캡처 |
| 규모 증거 | 고유 사업과 회차, 원문, 사례와 문서의 별도 집계, 용량과 주요 질의 시간 |

이는 팀 내부 권장안이다. 수업의 구체적인 제출 파일 형식, 발표 시간, 페이지 수와 우리 팀 발표일은 별도 공지 확인 항목이다.

공식 요구와의 대응은 [11 문서](11_과제_요구사항_충족_계획.md), 작업 순서와 중단 기준은 [마일스톤](BenefitLens_최종발표까지_마일스톤_계획.md)을 따른다.
