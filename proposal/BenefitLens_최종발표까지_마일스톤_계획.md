# BenefitLens 최종 발표까지의 마일스톤 계획

## 1. 계획의 기준

이 계획의 목표는 현재 제안서를 12월 최종 발표에서 동작하는 데이터 제품으로 보여주는 것이다. 강의 일정상 프로젝트 제안 발표는 10월 20일과 10월 22일, 동료평가는 10월 27일, 최종 발표는 12월 15일과 12월 17일이다. 제안 평가는 전체 성적의 20퍼센트, 최종 평가는 40퍼센트다.

과거 최종 발표 10개는 15쪽에서 30쪽 규모였고, 공통적으로 문제 정의, 실제 데이터, 전체 파이프라인, DB나 온톨로지, 처리 방법, 서비스 데모, 결과와 한계를 보여줬다. BenefitLens도 같은 깊이까지 가되, 학교는 POSTECH 한 곳으로 고정하고 재단, 기업과 국가는 각 3개 출처를 목표로 하며 전체 공지를 포괄한다고 주장하지 않는다.

최종 성공 장면은 다음과 같다.

> 사용자가 자신의 최소 정보를 입력해 검토할 공고를 찾고 근거와 수집 범위를 확인한다. 한 공고를 선택해 실제 경험 질문에 답하면 공식 문항에 맞는 개요와 초안이 생성된다. 초안의 각 주장은 사용자 답변까지 추적되고 미확인 사실은 표시된다.

## 3. 마일스톤별 해야 할 일과 이유

### M0. 문제와 기준점 고정

사용자 과제를 두 단계로 고정한다. 첫 과제는 “네 출처 범주에서 검토할 공고 두 개와 확인할 조건 찾기”, 둘째는 “공고 하나의 실제 문항에 맞는 첫 초안 만들기”다. 탐색 기준점은 사이트 북마크와 조건표, 작성 기준점은 빈 양식과 일반 대화형 AI다. 자동 신청, 합격 예측, 타인 문장 재사용, 허위 경험 생성, 전국 대학 확장과 장기 퀘스트는 제외한다.

이 단계가 필요한 이유는 단순 통합 검색과의 차이를 나중에 기술로 꾸며낼 수 없기 때문이다. 과거 발표들도 먼저 기존 방식과 제안 방식의 차이를 제시했다.

완료 조건은 대상 사용자, 최종 행동, 강한 기준점, 허용 주장과 금지 주장이 한 페이지에 함께 있는 것이다.

### M1. 출처와 권리 감사

학교는 POSTECH 한 곳을 선정하고 재단, 기업과 국가에서는 공고 출처를 세 개씩 선정한다. 별도로 신청 양식과 평가 기준, 사용자가 제공할 경험과 문체 필드, 이용이 허용된 기관 공개 자료를 정한다. 모든 출처에 URL, 운영기관 또는 작성자, 인증 여부, 형식, 갱신 주기, 이용 조건, 저장과 변환 및 표시 허용 범위를 기록한다. 공고는 범주별 10건, 작성 자료는 후보 15건을 검사한다. 인증 영역과 유료 자료는 우회 수집하지 않는다.

작성 자료는 공식 문항, 분석 이용이 허용된 공개 사례, 링크 안내만 가능한 후기, 제외 자료로 나눈다. 권리가 불명확한 후기는 URL과 메타데이터만 남기고 패턴 말뭉치에서 제외한다. 공개됐다는 사실이 재사용 허락을 뜻하지 않기 때문이다.

중단 기준은 한 계층에서도 합법적이고 반복 가능한 공고 출처를 확보하지 못하거나, 신청 유형 하나의 공식 문항을 얻지 못하는 경우다. 작성 자료가 부족하면 공식 양식과 평가 기준만 쓰는 구조화 인터뷰로 줄인다.

### M2. 데이터 탐색과 품질 기준

공고 표본에서는 결측, 날짜, 중복, 기관명 변형, PDF 비율, 수정 공고와 조건 복잡도를 측정한다. 판정 지침을 만든 뒤 사람이 검토한 공고 30건을 개발 세트로 만든다. 작성 자료에는 문항, 글자 수, 평가 항목과 서술 역할을 주석한다. 서술 역할은 동기, 상황, 행동, 근거, 결과, 배운 점과 향후 계획으로 시작하며 표본을 보고 수정한다. 공고 10건과 작성 자료 5건 이상은 두 사람이 독립 주석한다.

이 단계가 필요한 이유는 “데이터가 있다”와 “판정에 쓸 수 있다”가 다르기 때문이다. 제안 발표 전에 실제 데이터의 어려움과 처리 가능한 경계를 보여줘야 한다.

완료 조건은 두 자료군의 프로파일링, 주석 지침, 개발 세트와 알려진 누락 목록이 재현되는 것이다. 최종 성능에 사용할 공고 20건 이상과 작성 자료 3건 이상은 별도로 남긴다.

### M3. 스키마와 DB 질의

기회 탐색 ERD에 `writing_source`, `application_prompt`, `narrative_pattern`, `template_version`, `experience_fact`, `draft_version`, `claim_provenance`를 연결한다. 양식 변경 시 템플릿을 자동 수정하지 않고 재검토 필요로 막는다. 주장 계보는 사용자 발화의 출처이며 사실의 진위 증명이 아니므로 별도 확인 상태를 둔다.

필수 질의는 등록 출처 상태, 현재 공고, 변경 조건, 프로필 판정, 과거 판정 재현, 공고 버전에 맞는 신청 문항, 템플릿 산출 근거, 초안 주장별 사용자 근거와 미확인 주장 목록이다.

이 단계가 필요한 이유는 과거 발표에서 ERD나 온톨로지가 기술 설명의 중심이었고, 이 프로젝트에서는 누락과 변경을 설명하는 구조 자체가 제품이기 때문이다. 관계형 DB로 먼저 구현하며 그래프 DB는 필요성이 측정될 때만 검토한다.

### M4. 대표 출처를 관통하는 종단 파이프라인

대표 공고 출처 하나에서 수집, 원본 저장, 해시 비교, 정규화, 검토, 조건 판정과 API까지 실행한다. 다른 두 계층은 실제 표본의 게시일, 기간과 원문 연결을 확인한다. 동시에 신청 유형 하나에서 공식 문항을 구조화하고, 작성 자료 5건 이상을 서술 역할로 주석해 첫 질문 템플릿을 만든다. 가상 사용자의 확인된 답변만으로 개요를 생성하고 근거 없는 주장을 탐지한다.

이 단계가 필요한 이유는 10월 제안 발표가 아키텍처 그림만 보여주는 자리가 아니기 때문이다. 작은 범위라도 전체 흐름이 동작해야 이후 출처 확대의 위험을 알 수 있다.

완료 조건은 대표 출처의 갱신과 판정, 실패 경고가 재현되고, 한 신청 문항의 질문 템플릿과 사용자 답변 기반 개요가 반환되는 것이다.

### M5. 제안 발표

제안 발표는 10쪽에서 12쪽으로 구성한다. 두 사용자 과제와 기준점, 범위, 두 자료군의 실제 샘플과 권리 등급, 이중 파이프라인, ERD, 실제 질의, 기회에서 초안까지의 짧은 시연, 평가와 축소 조건을 포함한다.

이 단계가 필요한 이유는 수업이 제안에서 아이디어와 함께 수집, 전처리와 DB 관리를 평가하기 때문이다. 모든 기술 상자는 실제 코드, 테이블 또는 로그에 대응해야 한다.

발표 전 교수자에게 현재의 자연 발생 데이터 규모가 대규모 DB 요구에 맞는지 질문한다. 부족하다는 답을 받으면 공개된 과거 월별 원본과 공고 버전의 기간을 늘릴 수 있는지 먼저 확인하고, 반복 복제로 규모를 만들지는 않는다.

### M6. 동료평가 반영과 안정화

10월 27일 동료평가를 주장, 데이터, 기술, 사용성, 발표의 다섯 범주로 분류한다. 각 의견을 수용, 실험 필요, 범위 밖으로 판정하고 이유를 남긴다. 파서 샘플, 중복과 버전 판정, 조건 규칙, 데이터 계보에 대한 회귀 검증을 추가한다.

이 단계가 필요한 이유는 피드백을 기능 목록으로 모두 받아들이면 축소한 범위가 다시 커지기 때문이다. 이후 개발 범위를 증거에 따라 한 번만 재고정한다.

### M7. 최대 6개 출처와 자동 갱신

기본 공고 범위는 범주별 골드 출처 한 개씩 총 4개다. 운영 상한을 통과하면 학교는 POSTECH 한 곳으로 유지하고 재단, 기업과 국가만 각 3개까지 연결해 하루 한 번 갱신한다. 작성 자료는 공식 문항, 사용자가 동의해 제공한 입력, 합성 예시와 권리 감사에 통과한 사례 5건에서 10건으로 고정한다. 신청 양식 변경은 새 버전으로 남기고 기존 템플릿을 재검토 상태로 바꾼다.

이 단계가 필요한 이유는 과거 최종 발표가 실제 자동 수집, 데이터 규모와 저장 구조를 보여줬기 때문이다. 이 프로젝트에서는 파이프라인 실패를 숨기지 않는 관측 가능성이 핵심 기술 성과다.

운영 중 수동 검토가 주 60분을 넘으면 출처를 줄인다.

### M8. 사용자 제품 완성

최소 프로필, 세 계층 필터, 네 판정 상태, 근거, 원문, 수집 상태와 변경 이력 화면을 만든다. 공고를 선택하면 실제 신청 문항, 요구 내용과 경험 질문이 이어지고, 답변 확인 뒤 개요와 초안을 만든다. 초안에는 주장별 사용자 확인 출처, 미확인 사실과 누락 문항을 표시한다. 유사성 검사는 이용이 허용돼 보존한 작성 자료에만 적용한다.

이 단계가 필요한 이유는 최종 평가가 실제 문제를 해결하는 제품을 요구하고, 과거 발표도 대부분 대시보드나 웹 서비스 데모를 포함했기 때문이다.

완료 조건은 정상 탐색, 입력 누락, 출처 실패, 수정 공고, 근거 없는 초안 주장과 미완성 문항을 사용자가 구분하는 것이다.

### M9. 데이터, 사용자와 운영 평가

같은 기간의 등록 출처를 사람이 직접 확인해 수집 재현율, 중복 제거 정확도와 변경 반영 지연을 측정한다. M2에서 개발에 쓴 30건과 분리한 평가 공고 20건 이상에서 기간, 금액, 대상, 조건 추출 정확도와 근거 일치율을 잰다. 출처 계층, 문서 형식과 조건 유형이 평가 세트에 모두 들어가게 한다. 공고와 테스트 프로필의 조합에서는 상태별 정밀도와 재현율, 판정 보류율과 잘못된 `조건상 검토 가능` 비율을 보고한다.

동의한 성인 학생 8명에서 12명을 모집해 탐색에서는 직접 사이트와 BenefitLens를, 작성에서는 빈 양식 또는 일반 대화형 AI와 BenefitLens를 교차 비교한다. 탐색 시간, 놓친 공고와 조건 오류에 더해 문항 충족률, 사용자 입력에 없는 사실, 사용자 확인 출처 연결률, 첫 초안 시간과 수정량을 측정한다. 이 연결은 진실성 증명이 아니며 합격률도 측정하지 않는다.

이 단계가 필요한 이유는 데모가 동작한다는 사실만으로 Impact를 증명할 수 없기 때문이다. 결과가 나쁘면 실패를 숨기지 않고 어떤 부분이 검색보다 낫지 않았는지 발표한다.

### M10. 발표 동결과 리허설

12월 8일에 기능을 동결한다. 깨끗한 환경에서 수집부터 화면까지 재실행하고, 데모용 데이터 상태를 고정한다. 네트워크 실패에 대비해 같은 시나리오의 짧은 영상을 준비한다. 발표는 본문 18쪽에서 22쪽과 부록으로 구성한다.

본문 순서는 문제, 두 기준점, 범위, 두 자료군과 권리, 아키텍처, 조건 및 서술 역할 모델, 수집과 버전 관리, 제품, 기회에서 초안까지의 시연, 평가, 실패와 한계, 결론이다. 각 수치는 실행 로그나 평가 파일로 추적한다.

이 단계가 필요한 이유는 과거 발표 범위가 넓더라도 좋은 발표는 하나의 제품 흐름으로 연결됐기 때문이다. 발표 자료의 모든 수치는 실행 로그나 평가 파일로 추적할 수 있어야 한다.

### M11. 최종 발표와 보존

12월 15일 또는 17일에 정상 탐색, 수집 실패 공개, 수정 공고 재판정, 경험 질문과 초안 계보를 시연한다. 12월 22일 뒤 코드, 스키마, 두 출처 등록부, 주석 지침, 평가 결과와 알려진 한계를 보존한다. 재배포할 수 없는 원문은 남기지 않고 출처, 권리 판정, 해시와 재수집 방법만 보존한다.

이 단계가 필요한 이유는 데이터 엔지니어링 결과물이 한 번 실행된 화면이 아니라 다시 수집하고 판정을 재현할 수 있는 시스템이어야 하기 때문이다.

## 4. 매주 유지할 증거

매주 다음 다섯 파일을 갱신한다.

1. `source_registry`: 공고 및 작성 자료의 접근, 이용 조건과 허용된 변환
2. `pipeline_run_report`: 성공, 실패, 문서 수, 처리 시간과 비용
3. `quality_report`: 두 자료군의 정답 세트 대비 품질과 미처리 유형
4. `draft_lineage_report`: 템플릿 버전, 주장 근거, 미확인 사실과 유사성 검사
5. `decision_log`: 추가, 제거, 보류한 기능과 근거

이 기록이 쌓이면 최종 발표의 데이터 규모, 기술 성과, 실패와 한계를 마지막 주에 기억으로 재구성할 필요가 없다.
