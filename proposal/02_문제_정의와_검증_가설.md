# 문제 정의와 검증 가설

## 1. 사용자는 어디에서 막히는가

지원자는 기회를 찾고 신청할 때마다 `기회 탐색 → 자격 확인 → 기관별 문항 해석 → 자기 경험 재구성`을 반복한다. 첫 검증 도메인인 장학금만 보아도 학교, 재단, 기업과 국가의 공식 사이트를 따로 확인해야 한다. 공고마다 같은 조건을 다른 표현으로 쓰고, 접수 기간과 제출 증빙도 다르다. 검색 결과를 찾은 뒤에도 사용자는 다음을 직접 판단한다.

- 현재 접수 중인가?
- 내 학적, 거주지, 성적과 소득 조건에 맞는가?
- 입력하지 않은 정보 때문에 판단을 보류해야 하는가?
- 공고가 수정됐는가?
- 이 판단의 근거 문장은 어디인가?

여기까지 해결해도 신청서 작성 문제가 남는다. 공식 문항과 평가 기준, 작성 안내, 공개 수기와 후기는 서로 흩어져 있다. 사용자는 무엇을 써야 하는지 알면서도 자기 경험 중 어떤 장면을 고르고 어떤 순서로 설명할지 막힐 수 있다.

## 2. 검색 서비스로 충분하지 않은가

단순 검색은 관련 문서를 찾는다. BenefitLens는 등록 출처의 문서를 공통 구조로 바꾸고 사용자 조건과 대조한다. 검색 결과가 없을 때도 지원이 없다고 단정하지 않고, 어느 출처를 언제까지 정상적으로 확인했는지 함께 보여준다.

작성 단계에서도 일반적인 자기소개서 예시를 주는 데 그치지 않는다. 선택한 공고의 실제 문항과 글자 수를 기준으로 사용자의 경험을 질문하고, 생성된 주장마다 어떤 사용자 답변에서 나왔는지 기록한다.

## 3. 핵심 사용자 과제

### 과제 A: 기회 찾기

학교, 재단, 기업과 국가의 등록 출처에서 지금 검토할 공고 두 개를 고르고 각 공고에서 부족하거나 확인해야 할 조건을 찾는다.

### 과제 B: 첫 초안 만들기

공고 하나를 선택하고 공식 문항에 필요한 자신의 경험을 답한 뒤, 미확인 사실과 누락 문항이 표시된 첫 초안을 얻는다.

두 과제는 하나의 결정 흐름이다. 첫 단계의 출력인 `opportunity_version`이 두 번째 단계의 입력이 된다.

## 4. 검증 가설

### 탐색 가설

> 여러 범주의 공식 사이트를 직접 확인하는 방식보다, 수집 범위와 최신성을 공개하는 통합 보드가 검토할 공고와 확인할 조건을 더 빠르고 정확하게 찾게 하는가?

### 작성 가설

> 빈 신청서나 일반 대화형 AI보다, 공고 문항에 맞춘 경험 질문과 주장 계보가 입력하지 않은 사실을 만들지 않으면서 더 완전하고 수정하기 쉬운 첫 초안을 만드는가?

## 5. 주장하지 않는 것

- 전체 지원 생태계를 빠짐없이 수집했다는 주장
- 구조화된 조건이 맞으면 실제 신청이나 선발이 보장된다는 주장
- 수상작에서 자주 보인 구조가 합격 원인이라는 주장
- 생성된 초안에 포함된 사용자 진술이 사실이라는 보증
- BenefitLens 사용이 실제 합격률을 높인다는 주장
