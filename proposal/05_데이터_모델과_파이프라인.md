# 데이터 모델과 파이프라인

이 문서는 목표 구조다. 2026년 10월 4일 구현 정본은 [데이터 추출 계약](../docs/데이터_추출_계약.md)과 [통합 자격 판정 기준](../docs/통합_자격_판정_기준.md)을 따른다. 현재 `opportunity`는 원천 공고 식별자이며 사업과 모집 회차의 상위 통합은 미구현이다. 원본은 PostgreSQL 바이트로 저장하고, 사용자 비교와 준비 초안은 브라우저에서 처리한다. LLM 초안 생성과 서버의 주장 계보는 목표 기능이다.

## 1. 왜 데이터 모델이 제품 기능인가

공고 목록만 저장하면 수집 실패와 실제 공고 부재를 구분할 수 없다. 현재 값만 저장하면 수정 공고가 들어왔을 때 과거 판정의 근거를 재현할 수 없다. 신청 문항과 템플릿의 버전이 없으면 오래된 양식에 맞춘 초안을 만들 수 있다.

따라서 데이터 모델은 내부 구현 설명을 넘어 다음 사용자 질문에 답해야 한다.

- 어디까지 정상적으로 수집했는가?
- 왜 이 공고가 이 상태로 분류됐는가?
- 어떤 조건이 언제 바뀌었는가?
- 이 초안은 어느 문항 버전과 사용자 답변으로 만들어졌는가?

## 2. 기회 탐색 모델

| 엔터티 | 저장 내용 |
|---|---|
| `source_scope` | 계층, 기관, URL, 포함 범위, 갱신 주기와 이용 조건 |
| `crawl_run` | 실행 시각, 접속과 파싱 상태, 발견 및 미처리 문서 수 |
| `raw_document` | 원문 위치, 해시, 수집 시각과 보존 정책 |
| `opportunity` | 사업의 지속 식별자, 운영기관과 지원 형태 |
| `opportunity_version` | 모집 회차, 접수 기간, `record_kind`, 다섯 요약 항목 `presentation_json`과 변경 내용 |
| `eligibility_rule` | 학적, 거주지, 연령, 성적, 소득, 중복 제한과 논리 구조 |
| `evidence` | 정규화한 값의 원문 근거와 위치 |
| `profile_snapshot` | 사용자가 동의해 입력한 최소 정보와 시점 |
| `evaluation` | 판정 상태, 공고와 규칙 버전, 판정 시각 |

조건 모델은 AND, OR, 예외, 명시적 미충족과 입력 누락을 구분한다. 수집 실패를 조건 미충족으로 바꾸지 않는다.

화면 요약은 지원 자격, 선발 및 제출 조건, 혜택, 의무와 제한을 담은 특약, 기간으로 구분한다. 이 자유 서술과 실제 비교용 규칙은 별개다. 학교와 학과는 고정 코드로 비교하고, 불명확한 원문은 판정을 보류한다. `policy`는 제도 안내이므로 모집 기간이 확인되지 않으면 접수 가능이 아니다.

## 3. 작성 지원 모델

| 엔터티 | 저장 내용 |
|---|---|
| `writing_source` | 자료 유형, 출처, 이용 조건, 저장과 분석 허용 범위 |
| `application_prompt` | 공고 버전별 문항, 글자 수, 요구 내용과 평가 항목 |
| `narrative_pattern` | 허용 자료에서 얻은 서술 역할과 산출 근거 |
| `template_version` | 적용 문항, 질문 순서, 포함 규칙과 검토 상태 |
| `experience_fact` | 사용자가 입력하고 확인한 경험과 선택적 증빙 메모 |
| `draft_version` | 사용 문항, 템플릿, 사용자 사실과 생성 시점 |
| `claim_provenance` | 초안 주장과 사용자 답변 또는 미확인 상태의 연결 |

`opportunity_version`과 `application_prompt`의 연결이 두 단계를 하나로 만든다. 양식이 바뀌면 연결된 `template_version`을 재검토 상태로 전환한다.

## 4. 두 파이프라인

### 파이프라인 A: 기회 탐색

```text
등록 출처 수집
→ 원본과 실행 상태 저장
→ 신규 및 변경 문서 식별
→ 기간, 금액, 대상과 조건 후보 추출
→ 공통 조건 스키마로 정규화
→ 규칙 검사와 사람 표본 검토
→ 공고 버전과 원문 근거 연결
→ 사용자 프로필과 조건 대조
→ 판정과 수집 범위를 함께 반환
```

### 파이프라인 B: 신청 초안

```text
공식 신청 양식과 허용 작성 자료 수집
→ 권리 등급과 원본 버전 저장
→ 문항, 글자 수와 평가 항목 정규화
→ 서술 역할 주석과 구조 패턴 집계
→ 문항별 경험 질문 템플릿 생성
→ 사용자 답변 확인
→ 개요와 초안 생성
→ 주장 계보, 누락 문항과 허용 자료 유사성 검사
```

## 5. LLM과 규칙의 역할

LLM은 조건 후보와 서술 역할 추출, 경험 질문과 초안 생성에 사용한다. 자격 상태는 검증된 구조와 규칙으로 계산한다. 초안 생성은 확인된 사용자 입력만 사용하며, 입력이 부족하면 추가 질문을 반환한다.

관계형 테이블과 연결 테이블로 필요한 질의를 표현할 수 있으므로 첫 버전은 PostgreSQL을 사용한다. 그래프 DB는 실제 질의 성능이나 모델링 한계가 확인될 때만 검토한다.

## 6. 최종 발표에서 통과해야 할 질의

1. 등록 출처별 마지막 성공과 실패 상태
2. 현재 접수 중인 공고와 최근 변경 조건
3. 프로필별 판정, 사용한 규칙과 원문 근거
4. 과거 공고 버전을 사용한 판정 재현
5. 선택한 공고 버전에 맞는 신청 문항
6. 템플릿의 작성 자료와 주석 근거
7. 초안 주장별 사용자 답변과 미확인 주장
8. 신청 양식 변경으로 재검토가 필요한 템플릿
