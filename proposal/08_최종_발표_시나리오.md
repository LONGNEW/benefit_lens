# 최종 발표 시나리오

## 1. 발표의 중심 문장

> BenefitLens는 어디까지 공고를 확인했는지 밝히고, 그 범위 안에서 왜 이 공고를 검토해야 하며 어떤 사용자 답변으로 초안이 만들어졌는지 재현한다.

## 2. 발표 구성

| 순서 | 내용 | 보여줄 증거 |
|---|---|---|
| 1 | 문제와 두 사용자 과제 | 기존 탐색과 작성 흐름, 기준점 |
| 2 | 범위 계약 | POSTECH 재학생, 네 출처 범주, 등록 출처 |
| 3 | 실제 데이터 | 공고 표본, 신청 양식, 권리 등급과 누락 |
| 4 | 데이터 모델 | 공고, 문항, 템플릿, 사용자 답변과 초안 계보 |
| 5 | 파이프라인 | 수집, 정규화, 버전, 질의와 생성 |
| 6 | 제품 시연 | 기회 탐색에서 첫 초안까지 |
| 7 | 평가 | 데이터 품질, 사용자 비교와 운영 비용 |
| 8 | 실패와 한계 | 미수집 출처, 보류 판정, 권리와 일반화 한계 |

본문은 18쪽에서 22쪽으로 구성하고, 세부 스키마와 추가 오류 사례는 부록에 둔다.

## 3. 핵심 시연

### 장면 1: 수집 범위를 먼저 보여준다

학교, 재단, 기업과 국가의 등록 출처와 마지막 수집 성공 시각을 보여준다. 한 출처의 파서 실패를 재현하고 결과 화면이 불완전하다고 표시하는지 확인한다.

이 장면은 결과가 없는 상황과 수집하지 못한 상황을 구분한다는 데이터 엔지니어링 가치를 보여준다.

### 장면 2: 공고 판정의 근거를 추적한다

학생 프로필을 입력하면 공고가 네 상태로 나뉜다. 공고 하나를 열어 조건 값, 근거 문장과 공식 원문을 확인한다. 학점이나 거주지 값을 바꾸어 영향받는 판정만 달라지는지 보여준다.

### 장면 3: 수정 공고를 반영한다

수정 공고를 수집하고 이전 버전과 달라진 조건을 보여준다. 과거 판정은 당시 버전으로 재현하고 현재 판정은 새 규칙으로 계산한다.

### 장면 4: 기회에서 초안으로 이동한다

검토 가능한 공고 하나를 선택한다. 해당 회차의 공식 신청 문항, 글자 수, 요구 내용과 템플릿 검토 상태를 불러온다.

사용자가 자신의 경험 질문에 답하면 개요와 첫 초안이 만들어진다. 초안의 각 주장을 클릭해 어느 사용자 답변에서 나왔는지 보여주고, 입력에 없는 사실과 미완성 문항을 표시한다. 외부 LLM 전에는 브라우저 내 결정적 기준선으로 같은 입력과 근거 계약을 시연한다.

### 장면 5: 양식 변경을 안전하게 처리한다

신청 양식의 문항을 변경한 새 버전을 넣는다. 기존 템플릿이 자동으로 사용되지 않고 재검토 필요 상태가 되는지 보여준다.

## 4. 발표에서 받을 자연스러운 질문

### 모든 공고를 수집한 것인가

아니다. 등록 출처와 수집 기간을 화면에 공개하고, 평가도 그 범위 안에서만 수행한다.

### 조건상 검토 가능이면 신청할 수 있는가

구조화한 명시 조건이 현재 입력과 맞는다는 뜻이다. 기관 심사, 미수집 조건과 증빙 확인이 남아 있으므로 공식 원문 확인이 필요하다.

### 후기 몇 개로 합격 패턴을 알 수 있는가

알 수 없다. 후기 구조는 경험 질문과 문단 완결성을 돕는 데만 사용하고 합격 원인이나 합격률로 해석하지 않는다.

### 일반 대화형 AI와 무엇이 다른가

선택한 공고 버전, 공식 문항, 검토된 템플릿, 사용자 답변과 초안 주장이 데이터베이스에서 연결된다. 공고나 양식이 바뀌었을 때 어떤 결과를 다시 검토해야 하는지도 추적한다.

### 타인의 글을 베끼게 되는가

패턴 분석이 허용된 자료에서 문장 대신 서술 역할을 추출한다. 허락이 불명확한 후기는 링크 안내에만 사용하고, 출력에는 사용자의 확인된 경험만 넣는다.

## 5. 데모 실패 대비

- 발표용 데이터 상태와 공고 버전을 고정한다.
- 같은 시나리오의 짧은 백업 영상을 준비한다.
- 네트워크 장애가 나면 저장된 실행 로그와 질의 결과로 파이프라인을 설명한다.
- 모든 발표 수치는 실행 로그와 평가 파일에서 다시 계산할 수 있게 한다.
