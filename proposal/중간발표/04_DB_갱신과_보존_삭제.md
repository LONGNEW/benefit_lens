# 원본 저장과 개인별 조회를 연결하는 DB 관리와 파이프라인

## 두 단계 서비스와 전체 데이터 흐름

첫 단계는 학생의 기본 조건과 원하는 혜택에 맞는 지원 기회를 찾는 것이다. 두 번째는 선택한 프로그램의 경험 자료와 작성 패턴에서 필요한 사용자 경험을 받아 초안을 준비하는 것이다. DB는 원본, 구조화된 공고와 프로그램별 작성 지식을 연결한다. 수집과 패턴 정리는 오프라인 배치에서, 학생 프로필에 따른 조회와 추가 질문은 온라인에서 처리한다.

```text
[오프라인 정기 배치]
검색 사전 → 검색과 크롤링 → 원본과 첨부 보존
   ↑                            ↓
 새 표현 ← 문서 역할 분류 ← 텍스트 추출과 필요 구역 OCR
                                ↓
             기관과 사업 및 회차 통합 → 조건과 혜택 추출
                                ↓
                    구조와 근거 검사 → 공고 저장
                                ↓
            프로그램별 경험 탐색 → 사례별 텍스트와 그림 해석
                    ↑                     ↓
                  새 표현 ← 사례 비교 → 작성 패턴 저장

[온라인 사용자 요청]
학생 기본정보 → 저장된 조건 비교 → 기본 조건 결과와 혜택
                                            ↓
                         공고 선택 → 추가 자격 질문과 요구사항
                                            ↓
             저장된 패턴과 현재 문항 → 빈칸과 필요한 경험 질문
                                            ↓
                        사용자 답변 확인 → 문항에 맞는 초안
```

수집 문서는 사업과 회차로 나눠 조건을 추출한다. 경험은 한 사례의 문서 전체 또는 연결된 구간을 읽고 프로그램 안에서 종합한다. 텍스트만으로 의미가 남지 않는 표와 그림은 필요한 페이지를 멀티모달 LLM으로 읽는다. 구조화된 자격과 프로필의 비교는 코드로 수행하고, 작성 단계에서는 해당 프로그램의 패턴과 현재 문항을 불러온다.

기준일은 2026년 10월 15일이다. 10월 14일 원장을 보존하면서 새 공고 구조, 경험 지식과 로컬 조회 API를 추가했다. 전체 흐름 중 무인 LLM 배치, 그림 의미 해석과 예약 갱신은 후속 구현이다.

## 공고 한 행과 사례 묶음의 관계

조회 결과는 사용자가 생각한 하나의 큰 공고 표처럼 제공한다. 공고 한 건을 열면 자격, 혜택, 경험 사례와 작성 패턴이 함께 나온다. 실제 저장은 회차가 바뀔 때 같은 경험 자료를 반복 복사하지 않도록 다음처럼 나눈다.

| 추가한 저장소 | 키와 내용 | 조회에 쓰는 방식 |
|---|---|---|
| 원본 문서 | 원문 ID, URL, 응답 해시와 원본 버전 | 조건과 패턴의 근거 확인 |
| `opportunities` | `opportunity_id`, `program_id`, 회차, 종류, `eligibility JSONB`, 추가 자격 질문과 요구사항, `benefits JSONB`, 신청 정보 | 회차별 공고 한 행과 조건 및 혜택 검색 |
| `program_knowledge` | `program_id`, `experience_cases JSONB`, `writing_pattern JSONB`, 패턴 버전 | 해당 프로그램의 사례 배열과 패턴 한 묶음 |

두 테이블은 10월 15일 로컬 PostgreSQL에 실제 생성했다. 공고의 `program_id`로 작성 지식 한 건을 찾아 조회 객체에 합친다. 프로그램 키와 종류 및 처리 상태에 인덱스를 두었다. 기존 `opportunity` 테이블과 후보 124개는 보존했다.

대표 종류, 대상 단위와 회차 상태는 먼저 필터링할 컬럼으로 둔다. 자격의 AND와 OR 연결, 프로그램별 추가 질문과 사례 배열은 중첩 객체를 JSONB로 저장한다. 기본 필터로 좁힌 후보의 조건을 비교하고 빈번한 조건은 실제 조회량에 맞춰 인덱스와 요약 컬럼을 추가한다. JSONB 자체가 모든 조건 검색을 자동으로 빠르게 해 주는 것은 아니다.

초기 검색 결과에는 기본 조건 결과, 혜택, 모집 상태와 추가 질문 수를 함께 준다. 추가 자격에 답하면 해당 공고의 판정을 갱신하고, 서류 및 활동 요구사항은 체크리스트로 보여준다. 추가 질문 답변은 개인별 `opportunity_id + check_id`에 연결하며 공개 공고와 분리한다.

사례마다 지원 회차와 원문을 보존하며 다른 연도 자료는 구성 참고로만 사용한다. 현재 문항과 분량은 선택한 공고 회차에서 가져온다. 같은 프로그램 안에서도 문항이 크게 바뀌면 적용 범위를 기록한 새 패턴 버전을 만든다.

## 언제 다시 가져오고 무엇을 갱신하는가

초기 운영안은 Asia/Seoul 기준 공고를 매일 19시에, 경험 자료 목록은 매주 일요일 19시에 확인하는 것이다. 신규 기관 탐색과 기존 출처 갱신을 분리하고, 해외 출처는 실제 변경 기록을 보고 주기를 조정한다. 예약 실행은 아직 운영 로그를 확보해야 한다.

초기 탐색은 사전과 새 자료가 두 단계 연속 늘지 않는 조건으로 마친다. 정기 갱신은 출처별 새 글, 기존 본문과 첨부의 변경을 확인한다. 탐색 종료 여부와 갱신 배치의 성공 여부를 따로 기록한다. 로그에는 사전 버전, 검색 범위, 처리한 페이지, 새 공고와 사례, 남은 작업 및 실패를 둔다. 재시도 한도를 넘은 작업은 미완료로 남긴다.

| 수집 결과 | 처리 |
|---|---|
| 새 원문 | 원본 보존 후 문서 역할과 사업 및 회차 확인 |
| 같은 내용 | 기존 추출 재사용, 마지막 확인 시각 갱신 |
| 본문과 첨부 변경 | 새 원본 버전, 관련 자격과 혜택 또는 문항 재추출 |
| 새 경험 자료 또는 기존 경험의 변경 | 사람과 회차를 대조해 추가 또는 버전 갱신, 해당 프로그램 패턴 재계산 |
| 접속 실패 | 마지막 정상 버전 유지, 실패와 재시도 기록 |
| 접수 종료 | 현재 신청 목록에서 제외, 과거 회차와 작성 참고 자료로 보존 |

원문 해시와 추출 규격 및 프롬프트 버전이 같으면 추출을 재사용한다. 공식 자격이나 문항이 바뀌면 개인별 판정과 초안에 쓰는 버전도 바꾸고 이전 결과는 당시 버전과 연결해 보존한다. 새 패턴이 생겨도 사용자가 편집한 초안은 자동으로 덮어쓰지 않는다.

## 원본과 개인정보 및 삭제 관리

공고 원문과 구조화된 값, 경험 원문 링크와 패턴 버전을 연결한다. 개인 프로필과 경험은 공개 수집 자료와 접근 권한을 분리하고, 기존 데모의 브라우저 내 입력을 서버에 자동 적재하지 않는다.

마감과 재게시 때문에 원본을 물리 삭제하지 않는다. 삭제 의무나 개인정보 삭제 요청이 생기면 원문, 연결된 경험 조각과 파생 패턴을 따라 처리하고 필요한 최소 삭제 기록만 남긴다. 보관 기간, 백업 만료와 복원 후 재삭제 방식은 확정할 운영값이다. 이용 범위가 확인되지 않은 공개 지원서 전문은 생성 입력이나 웹 재배포에 자동 반영하지 않는다.

## 발표에서 보여줄 세 가지 흐름

| 예시 | 원문 입력과 전처리 | 프로필 비교 또는 작성 연결 |
|---|---|---|
| NVIDIA 펠로우십 | 공식 HTML의 자격과 혜택, 선정자의 제안서 PDF 텍스트 | 기본 박사 조건과 혜택 → 첫 학년과 예외에 대한 추가 확인 → 연구 경험 질문 |
| 관정 국내 학부 장학금 | 공식 HTML의 과정, 학기, 척도별 GPA와 장학 금액 | 박사 프로필의 학위 불일치 → 학부 예시 프로필로 바꿔 조건 비교 |
| Gates Cambridge 진학 지원 | 공식 자금 원장과 공개 에세이, 면접 후기 | 신규 진학 경로 선택 → 해당 프로그램의 경험과 기여 질문 |

세 예시는 현재 글자 텍스트가 있는 자료다. OCR은 텍스트가 없는 스캔을 입력했을 때만 분기하는 별도 시연으로 준비한다. 수행하지 않은 OCR이나 배치 LLM 결과를 실행 화면으로 제시하지 않는다.

발표 자료의 순서는 검색 사전과 종료 로그 → 원문 → 설명과 구조화된 조건 → DB의 공고 한 건 → 기본 조건과 혜택 → 프로그램별 작성 패턴 → 필요한 경험 질문이다. 실제로 완료된 대량 수집과 재적재 검증, 제안 스키마와 시연 예정 기능을 구분한다.
