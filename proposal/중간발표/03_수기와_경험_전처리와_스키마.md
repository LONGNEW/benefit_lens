# 프로그램별 경험과 작성 패턴의 전처리와 스키마

## 목적과 사용자에게 보일 결과

사용자가 지원 공고를 고르면 그 프로그램의 여러 경험에서 반복되는 작성 구조와 관점을 불러온다. 이를 공식 문항과 연결해 본인의 경험을 넣을 자리를 만들고, 비어 있는 정보만 질문한다. 프로그램별 패턴은 정기 배치에서 미리 정리한다.

공고 조회 결과 안에 `experience_cases[]`와 `writing_pattern`이 들어 있는 형태로 보여준다. 문서 기준일은 2026년 10월 15일이며 공개 원문을 읽어 만든 정성 분석과 자동 처리의 설계를 구분한다.

## 프로그램별 경험 검색 사전과 종료 조건

공고를 찾은 뒤 `프로그램 공식명과 별칭 + 지원서 또는 경험 표현`으로 검색한다. 시작 표현에는 합격 수기, 지원 후기, 면접 후기, 연구계획서, successful application, personal statement, research proposal, interview experience를 둔다. 국가와 언어를 바꿔 검색하고, 발견한 작성자의 공개 자료 목록과 관련 링크도 방문한다.

새 자료의 제목과 본문에서 문서 명칭, 프로그램 별칭, 선정 연도와 준비 표현을 뽑아 사전을 확장한다. 표현 정규화와 중복 처리는 [01 수집 방법](</home/longnew/Desktop/course_work/26-2 학기/데이터엔지니어링/benefitlens/proposal/중간발표/01_수집할_정보와_방법.md>)을 따른다. `표현, program_id, 언어, 근거 문서, 발견 단계`를 저장해 후속 검색과 연결한다.

한 단계의 대기 검색, 결과 페이지와 관련 링크를 처리한 뒤 신규 표현, 사례와 문서를 센다. 신규 검색 표현, 신규 사례와 새로 확보하거나 갱신한 문서가 모두 0개인 단계가 두 번 연속이면 그 프로그램의 초기 탐색을 종료한다. 첫 0개 단계 뒤에는 기존 사전으로 범위별 재탐색을 실행한다. 사례는 `사람 + 프로그램 + 지원 회차`로 구분하고, 같은 사례의 새 원문이나 의미 있는 내용 변경은 신규 또는 갱신 문서로 센다. 회차가 불명확하면 임시 연결을 남긴다.

사전이 같아도 새 사례나 새 문서가 나오면 계속 찾는다. 실패, 한도와 미방문 링크가 남으면 미완료로 기록한다. 프로그램마다 언어와 검색 범위, 단계별 수, 종료 이유를 저장하고 주기적 갱신에서 새 자료가 나오면 재개한다.

## 텍스트와 그림에서 정보를 추출하는 순서

1. 검색 결과를 실제 지원서, 개인 후기, 공식 인터뷰, 일반 작성 안내와 선정 기록으로 나누고 원문을 확보한다.
2. 텍스트와 캡션을 추출한다. 스캔에는 OCR을 적용하며, 도표나 그림이 작성 논리와 결과를 설명하면 해당 페이지를 멀티모달 LLM에도 제공한다.
3. 사람과 문서를 구분한다. 같은 사람의 지원서와 인터뷰, 재게시본은 하나의 사례에 연결한다.
4. LLM으로 준비, 서류 작성, 면접과 선정 후 활동을 구분한다. 문장과 그림이 맡는 역할, 작성자의 행동과 판단, 드러난 결과 및 명시한 관점을 근거와 함께 추출한다.
5. 같은 프로그램의 독립 사례를 비교해 반복되는 상위 관점, 문단 역할 순서와 서로 다른 접근을 작성 패턴으로 정리한다.
6. 해당 회차의 공식 문항에 연결하고 필요한 사용자 경험 항목을 만든다.

한 사례의 문서는 분량이 허용하면 전체를 읽힌다. 긴 문서는 절과 페이지로 나누되 문서 개요, 앞뒤 문맥과 그림 및 캡션을 연결한다. 사례별 결과를 만든 다음 같은 프로그램 안에서 종합한다. OCR은 글자를 읽는 역할이고, 그림의 비교 관계나 논지에 대한 해석은 별도 출력이다. 해석에는 페이지와 그림 위치를 붙인다.

LLM 출력은 단순한 조언 목록이 아니라 `반복 관점, 문단 역할의 연결, 근거 사례, 차이와 예외, 사용자에게 필요한 내용`이다. 작성자가 말하지 않은 마음가짐은 사실로 추정하지 않는다. 게시일, 지원 회차와 선정 확인은 별도 필드로 둔다.

## 원문에서 읽어 낸 프로그램별 구성

| 프로그램과 사례 | 원문의 근거 위치 | 구성에 대한 해석 |
|---|---|---|
| NVIDIA N1 | 1쪽의 연구 비전과 DISTAL, 2쪽의 NVIDIA 인턴십과 legate.sparse 및 남은 과제 | 사용자의 계산 문제 → 본인의 해결과 결과 → NVIDIA 기술과 연결 → 다음 연구. 한 사례에서 관찰한 구성 |
| Google G1 | 연구계획서 1쪽과 3쪽의 “Future Research After Graduation” | 하나의 문제 아래 기존 기여와 남은 박사 연구를 연결 |
| Google G2 | 1쪽의 문제 제기, 2~5쪽의 단계별 연구와 “Evaluation” | 기존 방법의 한계 → 제안 연구 단계 → 검증 방법 → 분야와 사회에 대한 기여 |
| Google G3 | 1~4쪽의 “Generalizability”, “Reliability”, “Interpretability” | 실제 활용의 문제를 연구 축으로 나누고 과거 결과와 앞으로의 연구를 연결 |
| Gates Cambridge C1 | 에세이 1쪽의 교육 봉사, 어려움과 수업 방식 변경, 향후 연구와 기여 | 문제를 만난 계기 → 구체적인 행동과 수정 → 관찰한 결과 → 진학 후 기여 |

Google G1~G3에서는 연구 문제, 본인의 선행 기여, 향후 계획과 의미를 연결하는 구성이 반복된다. N1과 C1은 해당 프로그램의 단일 작성 사례다. 프로그램별 사례 수를 표시하며 단일 사례에서 얻은 구성을 반복 관찰된 패턴과 구분한다.

G4는 비슷한 제안으로 이전 회차에 불합격했다고도 설명한다. 공개된 성공 사례의 공통 구성을 합격의 원인이나 확률로 해석하지 않는다. 공식 선정 사실과 지원서의 구성은 서로 다른 근거다.

## 후기에서 얻는 준비 과정과 마음가짐

[문경식 후기](https://blog.google/intl/ko-kr/company-news/outreach-initiatives/phd-fellowship-2025-kr-moon/)의 마지막 조언은 “왜 이 연구를 했는지, 이 연구가 어떤 문제를 해결하며, 앞으로 어디로 나아가고 싶은지”를 강조한다. [유재민 후기](https://blog.google/intl/ko-kr/company-news/outreach-initiatives/phd-fellowship-2025-kr-yoo/)와 [오상은 후기](https://blog.google/intl/ko-kr/company-news/outreach-initiatives/phd-fellowship-2025-kr-oh/)도 연구 방향과 활용 가치를 설명한 준비 경험으로 연결한다. 이 세 사람은 앞의 공개 작성 자료 여섯 명과 별도 사례다.

C1의 면접 후기는 자신의 제안 연구를 짧게 설명하고 예상되는 어려움, 본인의 봉사 경험과 공동체 기여를 준비했다고 서술한다. 이를 서류 문단 패턴과 분리해 면접 준비 질문에 연결한다. 과거 후기의 면접 시간과 마감일은 현재 지원 규정으로 복사하지 않는다.

## 프로그램 안에 들어갈 스키마

프로그램마다 `experience_cases[]`와 문항별 패턴 배열 `writing_pattern[]`을 둔다. 사례는 다음 필드를 가진다.

| 필드 | 내용 |
|---|---|
| `case_id`, `person_id`, `program_id` | 사례, 사람과 프로그램 식별 |
| `application_round`, `award_round` | 지원 회차와 수혜 회차. 모르면 null |
| `document_type`, `stage` | 실제 지원서, 후기, 인터뷰와 준비, 작성, 면접, 선정 후 단계 |
| `outcome_verification` | official, university_confirmed, self_reported, unknown |
| `fragments[]` | problem, motivation, action, decision, result, reflection, plan의 역할과 연결 |
| `visuals[]` | 페이지와 그림 위치, 캡션, 논지에 필요한 해석 및 연결된 조각 ID |
| `source_refs[]` | URL, 쪽 또는 절, 짧은 근거, 원문 버전과 이용 범위 |

`writing_pattern`은 문항별 패턴을 담는 한 묶음이다. 각 패턴에는 `insight, sections, supporting_case_ids, variations, required_inputs, source_rounds, target_round`를 둔다. `insight`는 여러 사례의 역할 연결에서 읽어 낸 상위 관점이고 `required_inputs`는 그 구성을 본인 글에 쓰기 위해 필요한 사실이다. 지원 사례 수와 다른 접근을 함께 저장하며 원문이나 문항이 바뀌면 버전을 갱신한다.

프로그램별 작성 패턴의 예시는 다음과 같다. 이는 읽은 자료로 정리한 제안 출력이며 배치 추출을 실행한 결과는 아니다.

```json
{
  "program_id": "google-phd-fellowship",
  "experience_cases": [
    {"case_id": "G1", "person_id": "hyeon-jeon", "application_round": "2024", "source_refs": [{"source_id": "hyeon-research", "locator": "1쪽과 3쪽"}]},
    {"case_id": "G2", "person_id": "julia-mendelsohn", "application_round": "2021", "source_refs": [{"source_id": "julia-proposal", "locator": "1~5쪽"}]},
    {"case_id": "G3", "person_id": "anjalie-field", "application_round": "2019", "source_refs": [{"source_id": "anjalie-proposal", "locator": "1~4쪽"}]}
  ],
  "writing_pattern": [{
    "pattern_id": "google-research-outline-v1",
    "basis": "observed_structure",
    "supporting_case_ids": ["G1", "G2", "G3"],
    "applicable_question_types": ["research_proposal", "research_impact"],
    "summary": "하나의 연구 문제에 기존 기여, 다음 검증과 기대 효과를 연결한다.",
    "insight": "연구 실적을 나열하는 대신 이미 한 일과 앞으로 할 일을 하나의 미해결 문제로 연결한다.",
    "variations": ["G2는 단계별 검증을 전개하고 G3는 세 연구 축으로 구성한다."],
    "required_inputs": ["해결할 문제", "본인의 기여와 근거", "다음 검증", "프로그램과 연결되는 기여"],
    "sections": [
      {"role": "problem", "ask": "누가 어떤 상황에서 어떤 한계를 겪었는가?"},
      {"role": "prior_contribution", "ask": "본인이 선택하고 수행한 일과 확인된 결과는 무엇인가?"},
      {"role": "next_plan", "ask": "남은 질문을 어떤 방법으로 검증할 것인가?"},
      {"role": "impact", "ask": "그 결과가 대상 프로그램과 사용자에게 왜 중요한가?"}
    ],
    "source_rounds": ["2024", "2021", "2019"],
    "target_round": null,
    "generation_status": "needs_current_prompt_alignment"
  }]
}
```

사용자가 공고를 고르면 `program_id`로 이 묶음을 조회하고 현재 문항과 맞는 패턴을 고른다. Google의 연구계획, 리더십과 면접은 서로 다른 문항별 구성이다. 한 사람에게서만 나온 구성은 단일 사례 관찰로 두고 반복 패턴과 구분한다. 실제 저장과 조회 객체의 관계는 [04 DB와 파이프라인](</home/longnew/Desktop/course_work/26-2 학기/데이터엔지니어링/benefitlens/proposal/중간발표/04_DB_갱신과_보존_삭제.md>)을 따른다.

## 빈칸과 사용자 입력에서 초안으로

패턴에서 먼저 다음과 같은 빈칸 개요를 만든다.

> [문제가 발생한 구체적인 상황]에서는 [기존 방식의 한계] 때문에 [대상]이 어려움을 겪었습니다. 저는 [본인의 판단과 행동]을 통해 [확인된 결과]를 얻었습니다. 다음으로 [검증할 질문]을 해결해 [프로그램 목적과 연결되는 기여]로 이어가고자 합니다.

이미 제공한 연구 경험이 있으면 그 사실을 해당 역할에 배치하고, 비어 있는 판단, 결과와 동기만 질문한다. 답변을 확인한 뒤 공식 문항과 분량에 맞는 초안을 작성한다. 문장마다 사용자 답변과 참고한 구성의 근거를 구분하고 타인의 경험을 신청자의 사실로 쓰지 않는다.

관정 공고는 “스스로 작성 할 것”을 안내한다. 지원처의 작성 정책을 확인하고 허용 범위 안에서 개요, 질문과 작성 보조를 제공한다. 현재 참조 규격의 `metadata_only`, `context_only`와 이용 범위 검토는 유지하며 사례 전문의 생성 입력과 재배포는 별도 승인 범위다.

## 발표에서 보여줄 자료

NVIDIA는 공개 제안서와 공식 안내를, 일반 장학금은 자격 필터링과 공식 작성 안내를, Gates Cambridge는 실제 에세이와 준비 후기를 보여준다. Google은 여러 독립 사례에서 작성 패턴 한 묶음을 도출하는 예시로 사용한다. 원문 → 사례 조각 → 프로그램별 패턴 → 빈칸 → 사용자 답변 → 초안의 순서를 표시한다.

현재 DB에는 경험 9개와 프로그램별 패턴 3개를 저장했고, 로컬 화면에서 원문 링크, 패턴과 빈칸 개요까지 연결했다. 그림의 의미 분석과 무인 LLM 배치 및 개인화 완성 초안 생성은 남아 있다. C1의 대학 보도는 이번 크롤러가 확보하지 못해 현재 적재본은 자기보고 확인으로 구분했다.
