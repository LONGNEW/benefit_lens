# 경험 원문 전체를 LLM으로 읽어 작성 패턴 추출

## 사용자에게 필요한 결과

학생이 공고를 고르면 그 프로그램의 다른 지원자들이 어떤 문제를 제시하고 경험과 계획을 연결했는지 확인한다. 서비스는 실제 원문에서 문단 역할과 관점을 추출하고 본인이 채울 사실을 질문한다.

## 입력 범위

학생 대상 예제는 10개이며 경험 자료가 있는 것은 Google, NVIDIA와 Gates Cambridge의 3개 프로그램이다. 현재 경험 문서는 Google 14개, NVIDIA 5개, Gates 6개로 합계 25개다. 지원서, 후기, 공식 인터뷰와 작성자의 공개 자료 목록을 포함한다. 사람 기준 사례는 Google 7개, NVIDIA 3개, Gates 4개다.

경험이 없는 7개 프로그램은 미확보로 표시한다. 광역 수집은 중지하고, 사용자가 지정한 경험 URL만 추가 확보했다.

패턴 수와 실제 입력 목록 및 추출 예제는 `docs/WRITING_PATTERN_EXAMPLES.md`에 기록한다. 단일 사례의 구성 관찰과 여러 사례의 비교를 구분한다.

## 변경한 추출 방식

이전에는 사람이 원문을 읽어 만든 패턴 JSON을 검증하고 적재했다. 현재 구현한 `writing_patterns.py`는 프로그램별 확보 경험의 전체 텍스트를 LLM에 전달한다. 입력에는 이전 `fragments`와 `writing_pattern`을 넣지 않는다.

1. `collection.json`에서 확보 완료한 경험 원문을 모두 읽는다.
2. 원문 텍스트의 SHA256을 대조하고 프로그램과 사례 ID에 연결한다.
3. 프로그램의 경험 문서 전체를 한 입력으로 LLM에 전달한다. 한도를 넘으면 잘라 보내지 않고 오류로 중단한다.
4. LLM은 문서별 분석, 사례별 역할과 근거 구절, 사례 간 작성 패턴과 평가 기준별 근거 및 선정과 미선정 사례의 관찰 비교를 JSON으로 출력한다.
5. 모든 문서와 사례가 출력에 포함됐는지 확인한다. 인용이 실제 원문에 있으며 해당 사례의 문서인지 검사한다.
6. 검증을 통과한 사례와 패턴을 표본 JSON과 `program_knowledge`에 저장한다. 입력 해시, 모델, 프롬프트 버전과 문서 수를 기록한다.

모델 실행은 로컬 Codex CLI를 호출하는 전처리 작업이다. 브라우저 검색과 원문 다운로드는 수행하지 않는다. 예제 로더는 이미 생성한 결과를 적재하므로 팀원의 기본 실행에는 LLM 로그인이 필요 없다.

## 출력 구조

| 출력 | 내용 |
|---|---|
| `document_analyses` | 입력 문서마다 읽어 낸 요약과 정확한 근거 구절 |
| `case_analyses` | 사례별 problem, action, result, plan 등 문단 역할과 원문 근거 |
| `writing_pattern` | 반복 관점, 문단 순서, 근거 사례, 차이와 필요한 사용자 사실 |
| `criterion_observations` | 공식 평가 기준에 연결한 주장, 본인 행동, 결과 근거와 기관 연결 및 한계 |
| `outcome_comparisons` | 선정과 미선정 양쪽 원문 인용, 관찰 차이와 비교 한계 및 사용자 질문 |
| 실행 기록 | 모델, 입력 원문 목록과 해시, 전체 글자 수와 생성 시각 |

여러 사례의 공통 구성과 단일 사례의 구성은 근거 사례 수로 구분한다. 지원서, 후기와 자료 목록은 증거의 성격이 다르므로 자료 목록만 읽고 제출 문단 구성을 추정하지 않는다. 패턴의 문단 제목과 필요한 사실 항목을 같은 길이로 맞춘다.

## 저장과 사용자 흐름

`program_knowledge` 한 행은 한 프로그램이다. 그 안의 `experience_cases[]`에 사례와 원문 근거를, `writing_pattern[]`에 모델이 추출한 패턴을 저장한다. 공고의 `program_id`로 연결한다.

공고 선택 → 공식 문항과 저장된 패턴 확인 → 빈칸 개요 → 사용자 사실 입력 → 문항별 초안 준비.

현재 화면은 빈칸 개요까지 제공한다. 사용자 답변을 받아 완성 문장으로 생성하는 연결은 다음 과제다. 타인의 경험을 사용자의 사실로 채우지 않는다.

## 재현

`make patterns COLLECTION="기존 collection.json의 절대 경로"`로 원문 분석을 실행하고 `make sample-db`로 결과를 적재한다. 원문이나 프롬프트가 같으면 검증한 결과를 재사용한다. 원문 파일은 로컬에 별도 보관하며 공개 Git에 포함하지 않는다.

양쪽 원문이 있는 경우만 결과별 비교를 만든다. 결과가 모호한 사례를 집단에 배정하지 않는다. 기존 글의 공통 구조는 지원 준비에 활용하고, 관찰한 차이를 실제 선정 이유나 합격 확률로 해석하지 않는다.

## 경험 전처리 단계 계약

입력은 프로그램 ID, 사례 ID와 결과 확인 수준, 확보한 경험 원문 전체, 현재 공식 문항과 평가 기준이다. 스키마는 `writing_patterns.py`의 `result_schema()`이며 `validate_result()`가 문서와 사례 연결, 인용 및 패턴의 필요한 사실 목록을 검사한다.

출력은 사례별 문단 역할, 프로그램별 작성 패턴과 질문, 평가 기준 관찰 및 가능한 결과별 비교다. `program_knowledge`에 저장하고 공고의 `program_id`로 검색한다. 이전 회차의 사례는 해당 연도를 보존하며 현재 문항으로 이름을 바꾸지 않는다.

NVIDIA의 `research-arc` 패턴은 사례 N1, N2, N3에 연결된다. 저장된 문단 역할은 “연구를 묶는 문제와 목표”, “핵심 기여와 근거”, “다음 단계 또는 지원의 효용”이다. 사용자는 각각 본인의 문제, 설계 판단과 실제 결과, 이후 계획을 채운다. 사례 본인의 성과를 사용자 성과로 복사하지 않는다.

`make pipeline-replay`는 전체 원문으로 입력 해시를 다시 만들고 그 해시에 해당하는 이전 모델 결과만 읽는다. 모든 인용과 사례를 재검증하고 표본의 패턴과 같은지 확인한다. 해시가 달라지면 중단하므로 과거 결과가 새 원문 분석처럼 표시되지 않는다. 신규 모델 분석은 별도 `make patterns` 경로다.
