# 회의 결론과 실행 계획

## 1. 확정한 방향

BenefitLens는 여러 기관에 흩어진 지원 기회를 모으고, 개인 조건으로 검토 대상을 좁힌 뒤, 기관 요구사항과 사용자의 확인된 경험을 연결해 첫 지원 초안을 준비하는 데이터 파이프라인이다.

현재 제품을 설명하는 한 문장은 다음과 같다.

> BenefitLens는 여러 기관에 흩어진 지원 기회를 공식 데이터로 수집하고 개인 조건으로 걸러, 사용자가 같은 경험을 기관별 요구에 맞춰 반복해서 재작성하는 비용을 줄이는 근거 기반 지원 준비 파이프라인이다.

장학금은 이 구조를 한 학기 안에 검증하기 위한 첫 도메인이다. 공모전, 취업, 연구실 지원과 연구과제 제안은 같은 패턴을 갖지만 이번 구현 범위에는 넣지 않는다.

## 2. 해결하려는 반복 작업

사용자는 지원할 때마다 다음 작업을 다시 한다.

1. 서로 다른 기관 사이트에서 현재 지원 가능한 기회를 찾는다.
2. 학적, 성적, 소득, 거주지와 경력 조건을 직접 비교한다.
3. 기관마다 다른 문항과 평가 기준을 해석한다.
4. 같은 경험을 요구사항에 맞춰 다시 고르고 재구성한다.
5. 작성한 문장의 사실과 근거를 다시 확인한다.

따라서 제품의 핵심은 검색 결과나 글 생성 하나가 아니다. `수집 → 정규화 → 최신성 관리 → 자격 조건 대조 → 요구사항 분석 → 경험 연결 → 초안과 근거 확인`이 끊기지 않는 것이 핵심이다.

## 3. 초기 데이터 범위

출처 포트폴리오는 네 범주로 관리한다.

| 범주 | 우선 출처 |
|---|---|
| 학교 | POSTECH 공통 장학제도, 대학원 재정지원, 전 학과의 공개 지원 페이지와 공고 |
| 재단 | 포스코청암재단, 미래에셋박현주재단, 일주학술문화재단 |
| 기업 연계 | 삼성꿈장학재단, SK행복나눔재단, 현대차 정몽구재단 |
| 국가 | 한국장학재단 공지, 한국장학재단 월간 학자금 데이터, 온통청년 API |

학교는 POSTECH 한 곳으로 고정하되 학교 전체와 학과별 지원을 수집한다. 재단, 기업과 국가는 각 3개 기관을 목표로 하며, 네 번째 기관은 수집 안정성과 운영 비용을 확인한 뒤 추가한다. 목표 포트폴리오는 10개 기관, 확장 상한은 13개 기관이다. 이는 크롤링 URL 10개로 제한한다는 뜻이 아니다.

이 목록은 구현 목표이며 현재 모두 활성화됐다는 뜻이 아니다. 범주별 첫 출처를 먼저 구현하고, 반복 수집과 공고 필드 품질을 통과한 출처만 활성 레지스트리에 승격한다. 상세한 완료 조건은 [BenefitLens 실행 기준](../docs/실행_기준.md)을 따른다.

범주는 탐색 포트폴리오이고 법적 기관 유형과는 다르다. 예를 들어 기업이 설립한 재단은 법적 유형을 `corporate_foundation`으로 보존하면서 탐색 범주는 기업으로 지정할 수 있다.

매일 오후 6시 수집은 운영 목표다. 스케줄러와 성공 시각이 실제로 기록되기 전에는 자동 갱신이 구현됐다고 발표하지 않는다.

## 4. 공통 스키마 계약

공고마다 표현이 달라도 다음 정보는 공통 구조로 보존한다.

| 영역 | 핵심 필드 |
|---|---|
| 출처와 기관 | `source_id`, `source_group`, `organization`, `official_url` |
| 공고 버전 | `opportunity_id`, `version_id`, `title`, `opens_at`, `closes_at`, `record_kind` |
| 화면 요약 | 자격, 제외, 우대, 요구사항, 혜택, 특약, 접수와 활동 기간을 `condition_sections_json`에 분리 |
| 혜택 | `benefit_type`, `description`, `amount_min`, `amount_max`, `currency`, `recurrence`, `amount_qualifier` |
| 자격 | `criterion_code`, `profile_field`, `operator`, `value_json`, `value_type`, `unit`, 조건 그룹 |
| 제출 | `required_document`, `application_prompt`, `character_limit` |
| 근거 | `raw_document_id`, `evidence_text`, `locator`, `collected_at` |
| 사용자 입력 | `experience_fact`, `writing_style_profile`, `confirmed_at` |
| 생성 결과 | `draft_version`, `claim_provenance`, `generator_kind` |

원문, 파싱 결과, 공개 확정본을 분리한다. 자격 조건은 일치, 불일치, 추가 확인 필요로 판정하고, 공식 원문과 사람 검토 없이 확정 상태로 승격하지 않는다.

실제 필드와 구현 상태는 [데이터 추출 계약](../docs/데이터_추출_계약.md)이 정본이다. 사용자 입력과 생성 결과의 서버 저장은 목표 구조이며 현재 데모는 브라우저에서 처리한다.

## 5. 지원서와 문체 데이터 정책

초안 품질을 높인다는 이유로 공개 자기소개서나 합격 수기를 무단 대량 수집하지 않는다. 데이터는 다음 우선순위로 사용한다.

1. 공식 신청 문항, 글자 수, 평가 기준과 기관 작성 안내
2. 사용자가 직접 입력하고 확인한 경험 사실
3. 사용자가 초안 작성 목적으로 제공한 자기 문체 샘플
4. 테스트를 위한 합성 예시
5. 별도 이용 허락을 확인한 공개 사례의 구조적 특성

권리가 불명확한 후기와 합격 사례는 링크와 최소 메타데이터만 보존하고 생성 입력과 학습 데이터에서 제외한다. 사용자 문체 샘플은 원문을 재사용하는 자료가 아니라 문장 길이와 말투 선호를 파악하는 입력으로만 사용하며 삭제 기한과 동의 상태를 기록한다. 이는 법률 판단이 아니라 프로젝트의 보수적 운영 기준이다.

## 6. 작은 종단 간 데모

데모는 다음 흐름을 한 화면에서 끝낸다.

1. 사용자가 최소 프로필을 입력한다.
2. 전체 검색 결과를 개인 조건과 접수 기간으로 판정한 뒤 접수 가능, 조건 미충족, 확인 필요, 접수 예정, 마감으로 분류한다.
3. 사용자가 공고 하나를 선택한다.
4. 지원 자격, 조건, 혜택, 특약, 기간을 짧게 보여주고 전체 근거와 공식 링크는 펼쳐서 확인한다.
5. 상황, 행동, 결과, 배운 점, 향후 계획과 원하는 문체를 입력한다.
6. 확인된 입력만으로 첫 초안을 만든다.
7. 초안의 문장이 어느 공고 필드와 사용자 입력에서 왔는지 표시한다.

현재 웹 데모의 생성기는 개인정보를 외부로 보내지 않는 결정적 기준선으로 구현한다. 이 기준선은 결과 재현성과 주장 계보를 먼저 검증하기 위한 것이다. 이후 같은 입력과 출력 계약을 유지하면서 LLM 생성기를 마지막 단계에 연결한다. LLM 연결 전후 모두 입력에 없는 성과, 수치와 경험은 만들지 않는다.

## 7. 발표에서 강조할 순서

1. 기회를 찾고 지원서를 맞추는 반복 작업이 여러 기관에 분산돼 있다는 문제를 한 문장으로 설명한다.
2. 장학금을 첫 검증 도메인으로 선택한 이유를 데이터 접근성과 사용 가능성으로 설명한다.
3. 서로 다른 출처가 공통 스키마와 버전으로 합쳐지는 과정을 보여준다.
4. 조건 판정의 근거와 누락 정보를 보여준다.
5. 확인된 개인 경험만으로 초안을 만들고 문장별 근거를 추적한다.
6. QR 코드로 같은 데모를 직접 실행하게 한다.

LLM은 마지막 응용 단계다. 발표의 중심은 이질적인 출처를 안정적으로 수집하고 변경을 관리하며, 근거가 있는 후보와 생성 입력을 만드는 데이터 엔지니어링 파이프라인이다.

## 8. 완료 기준

- 과거 주제의 코드, 문서와 자산이 활성 프로젝트에 없다.
- 네 출처 범주가 레지스트리에 명시되고 범주별 골드 세트가 있다.
- 공통 스키마가 자격, 혜택, 필수 서류, 실제 문항과 초안 근거를 표현한다.
- 웹에서 프로필 입력부터 공고 선택과 근거 기반 초안까지 이어진다.
- 테스트, 린트와 프로덕션 빌드가 통과한다.
- 발표 자료가 구현된 기능과 계획 중인 기능을 구분한다.
